# Logs

All logs go to the data partition, one folder per day: `/data/.r1metal/logs/yyyymmdd`, by the device clock. A past day is packed into `yyyymmdd.tar.gz` next to it. The debug screen's `LOG` switch turns all logging off, the kernel's included, or adds every debug line and a record of every frame. `r1 logs` copies the logs to `logs/device` in the workspace (git ignores `logs/`); `r1 logs -f` follows the log live.

## Daily files

Every line starts with the local time of the event (`19:29:42.031`).

| File | Content |
|---|---|
| `log` | every kernel log record as `/dev/kmsg` returns it (`level,number,microseconds,flags;text` plus dictionary lines). The firmware's own lines are records in it (`grep r1metal:`). Lines that are not records start with `--`: `-- boot ID` where a boot starts, `-- records N to M were not kept` where records are missing |
| `frames` | at the level `debug` alone ([The logging switch](#the-logging-switch)), one record per frame of an animation: its number in the run, when it was shown, draw and present times |
| `input` | every touch, wheel and button event; a finger on a keyboard without its position |
| `power` | the battery reading every second (voltage, current, charge counter, temperature, level, charger state), including the readings taken while the screen is dark |
| `state` | snapshots: uptime, load, memory, CPU times, interrupts per core, disk and network counters, suspend statistics, the clock of the large cores and of the small ones and the most their policies let each have, the chip's thermal zone by its type and temperature (`thermal_zone3`), every process's state and CPU time (`/proc/*/stat`) and each firmware thread's (`/proc/self/task/*/stat`). Taken when logging starts, at every sleep and wake, at every percent of battery, and as a call's sound starts and stops (`call talked in`, `call over`, [Calls](../app/calls.md#the-log)) |
| `crash/` | the crash store and what the bootloader saved of a crashed boot, one file per record as `HHMMSS-NAME`, by the time it was copied |

Next to the day folders, `logs/boot` names the boot whose kernel log was last read, `logs/crashes` lists the crash store records already copied, and `logs/scrubbed`, while it is kept, names the boot Signal's traces were last taken out in ([Unlink](#unlink)).

The logs contain network names, hardware and network addresses, and, in the kernel's own record of its command line, the serial number and the IMEI. The firmware's copy of the command line omits every value that identifies the device (`r1_funcore::domain::device::to_log_cmdline`), and so does the USB console. The folder is under `.r1metal`, which is encrypted and hidden from USB hosts; the writer opens it once the safe is open, reading the kernel's log from its beginning ([Storage](storage.md#the-safe)).

## The writer

One thread, `logs`, writes everything (`crates/impshell/src/storage/logs/`). Formats and decisions live in `r1_funcore::logs`: names, lines and their timestamps, notes and snapshots, when the writer opens, closes and commits (`Switch`, `should_commit`) and how often it gathers (`GATHER_PERIOD`), the queue lines wait in and when a wait for it to be written is over (`Queue`), the days the writer and the packer are at and whether the packer is held off (`Days`), the sequence of kernel records, the clock marks, repairing a file's end, the list of copied crash records, and what of a day's files tells of Signal ([Unlink](#unlink)). Archive blocks, written and read, are `r1_funcore::fs::tar`.

- The kernel buffers 512 KiB of records (`CONFIG_LOG_BUF_SHIFT=19`). Once a second (`GATHER_PERIOD`) the thread reads all new records from `/dev/kmsg` and writes each file its lines.
- While debug records are logged, a waiting record also wakes the thread: with the radio on they can come faster than the buffer holds for a second. A snapshot request and `logs::settle` wake it at once.
- `logs::settle` returns once everything is written (before a suspend, restart or power off), or after 10 s (`power::SHUTDOWN_TIMEOUT`) with whatever is not, so a stuck writer never blocks shutdown; the log then says so.
- **Handing over lines never waits for the writer.** A thread collects its lines in its own list (`THREAD_QUEUE` in `storage/logs/mod.rs`) and passes them on with `try_lock` only: into the writer's queue if it is free, otherwise into a parking area (`overflow` in `Shared`), tried the same way. The writer's pass (`Shared::take_overflow`) and the next successful handover take in what is parked. Every line carries the number of its logging period (`Shared::begin_period`); lines from an earlier period are dropped. The main loop takes the writer's lock when the switch changes (`Logs::want`) and as it takes a status the writer told (`Logs::latest`).
- **Timestamps.** A record is stamped with the time it was made. Every 60th pass (`MARK_PERIOD`), once a minute and more often while debug records wake the thread, the writer logs `logs: clock N` at debug level, with the monotonic clock in microseconds; this ties the kernel's clock to the time of day to the millisecond. A mark that took over a millisecond to make is skipped. The kernel stamps records made while entering a suspend with the resume time.
- **Restarts.** `log` starts at record 0. A second run of the firmware within one boot continues after the last record the file holds. During sleep the thread is frozen and the kernel writes the files out while entering the suspend. Trailing zero bytes left by a crashed kernel are cut when the folder is next opened.
- **Commits.** All of a day's files are committed whenever `log` has grown by half the crash store size (`ramoops.console_size` on the command line: 128 KiB of 256), so the kernel's last output is always either in the crash store or committed. A kernel crash loses frames, input and readings since the last commit; an app crash loses at most a second of them.

## The crash store

After a kernel crash the bootloader saves what the kernel left on the `expdb` partition: a table at its start (`r1_funcore::fs::kedump`) and the parts it lists, among them the SRAM's reboot record (`SYS_RAMCONSOLE_RAW`), the crash store (`SYS_PSTORE_RAW`), ATF's log (`SYS_ATF_LAST`) and the bootloader's own log of the dump (`SYS_LOG_DUR_LKDUMP`). While the table exists, the bootloader writes that record back into SRAM and the console back into the crash store at every start, cold or warm; a warm start then reports `androidboot.bootreason=kernel_panic`. The kernel shows the record it found in `/proc/aed/reboot-reason`; its `oops_in_progress` address identifies the build that wrote it.

`CONFIG_PSTORE_CONSOLE` keeps 256 KiB of the kernel's console (`/sys/fs/pstore/console-ramoops-0`, all but debug records). At start it holds a crashed boot's console as the bootloader restored it, or after a warm restart the end of the previous boot (last line `reboot: Restarting system`); after a cold start it is empty. At the first open of a run the writer copies into `crash/`:

| File | Content |
|---|---|
| `HHMMSS-console-ramoops-0` | the crash store, once: its name, length and CRC32 are recorded in `logs/crashes`. A store whose last line is an orderly shutdown (`reboot: Restarting system`, `reboot: System halted`, `reboot: Power down`) is recorded but not copied (`Crashes::add_record`) |
| `HHMMSS-expdb` | the table and every part it lists |
| `HHMMSS-reboot-reason` | `/proc/aed/reboot-reason` |

Once those copies are committed, the table is zeroed (`take_dump` in `storage/logs/crashes.rs`), as on an R1 that never crashed. A table longer than its partition, or one that lists more than the partition holds, is reported and left alone (`kedump::check_table`, `kedump::check_parts`). The crash store is never cleared. With logging off nothing is copied and the table stays. While the mark of a scrub is kept, every copy is written with Signal's lines blanked ([Unlink](#unlink)).

## Archives

At a change of day and at a run's first open, every folder except today's is packed into a gzip ustar archive (`flate2`), committed, and removed. An existing archive is never overwritten (`yyyymmdd_1.tar.gz`). The `logs pack` thread runs behind every other thread and never packs the day the writer has open; no thread that draws waits for it, and the writer waits for the day it packs only to open that day (`Shared::open_day`) or to scrub (`Writer::scrub`). Nothing is ever deleted but what Signal's unlink takes out (below).

## Unlink

When the phone unlinks the R1, Signal's thread asks the writer to take out what tells of Signal (`logs::scrub`) and waits until it has ([Signal](../app/signal.md#unlink)). The writer does it once the settings are read and its pass has written what the kernel and the threads made before the asking, the packer held off meanwhile (`Days::hold_packer`) and the open day's files closed, to be opened anew in their new place (`Writer::scrub`, `storage/logs/scrub.rs`). A line tells of Signal where the firmware wrote it of Signal (`r1metal: signal: `) or one of Signal's threads made it, by the kernel's tag of the thread (`[pid:signal]`, `auto`, `drafts`, `drafter`; `scrub::is_signal_line`); the snapshots' lines of every process and thread, which every device has whether it was ever linked or not, are none. What a file is to the scrub is told by its path before it is read (`scrub::to_holding`). In every day's folder and every archive:

- `log`: such a record keeps its stamp and its head (`19:29:42.031 14,130401,7564029328,-;`), by which the records after it stay numbered and a second run of one boot carries on, and loses its text and the dictionary lines behind it; any other such line goes.
- `crash/`: such a line is overwritten with blanks, its line end kept, as the bootloader lays its saved parts out by where each begins.
- Other files hold nothing of Signal's, are not read and stay as they are.

A log and an archive are read as they are written, twice: once to tell whether anything goes, with the size each file comes to, and once more to write. A log passes through `scrub::LogScrub` in pieces, of which no more than a line is held, and an archive a file of its tape at a time, so a scrub takes no more memory than a line of a log or a crash's copy, however large the day. A file that changed is written anew beside itself and put in its place; an archive that changed is packed anew, its files in their order with their times; one that cannot be read as a gzipped tape goes, and so does whatever a cut write left half written.

Before anything is taken out, the writer keeps the boot's name in `logs/scrubbed` (`logs::SCRUBBED`): the crash store's console and a dump the bootloader saved may still hold lines from before the scrub, and reach `crash/` only at a later first open. While the file is kept, every copy made there is written with Signal's lines blanked, as a scrub blanks the copies in a day's folder (`take_crashes`, `take_dump`); it goes once the copies were taken in another boot than the scrub's, whose own lines the crash store then holds no more (`scrub::is_mark_spent`). Then syslog's clear (`SYSLOG_ACTION_CLEAR`, `klog::clear`) has a crash's dump, which pstore carries onto the partition at the next start, begin after what the kernel holds now. The packer is let go and asked for the days it passed over. What failed is told to Signal's thread, whose next start tries again.

## The logging switch

The debug screen's `LOG` line shows `ON`, `DEBUG` or `OFF`; a click cycles on, debug, off, on. `r1 sh log off|on|debug` sets it from the host ([Console](console.md#verbs)). The `LOG FILES` line shows the writer's state: `ON 20261011` with the folder, `OFF`, `WAITING FOR THE SETTINGS`, or the error. A folder that could not be written is not retried until logging is switched off and on.

The switch is the setting `logging off|on|debug`. The app sets the kernel's two switches from it (`klog::set`: `/sys/module/printk/parameters/silent` and `debug`): silence first when turning off and last when turning on, and the firmware's own switch around the kernel's, so the debug call sites change once and the firmware never writes to a kernel that stores nothing. Process 1 follows the kernel's switch whenever it starts the app and after the app exits (`klog::follow_kernel`).

| Level | Effect |
|---|---|
| on | Every record from emergency to info is stored. The kernel drops its own debug records before creating them (`printk.debug` unset, kernel patch `0188`); a program's record keeps its level |
| debug | The kernel stores its debug records too, and every debug call site prints: dynamic debug call sites (`0189`) and the drivers' own switches: the gauge's log level (`0195`), mt6370's (`0196`), the display's levels, its mobile log and its MIPI TX register trace (`0197`), every thermal zone and cooler the R1 builds (`0199`), the USB controller and its queue unit (`0200`), WMT, STP, their transports, WMT detect, the combo stub and the thermal query dump (module patch `0055`), and every gen4m log class (module patch `0056`). Each driver reads its switch when it prints, and each line keeps the level it prints at. The app makes a record of every frame, for the `frames` file and the console (`logs::are_frames_read`) |
| off | Nothing is logged. The files are closed, the thread sleeps, and every logging call returns after checking one flag. The firmware writes nothing to the kernel log or the USB console (the console still answers commands). The kernel stores nothing: `printk.silent` (kernel patch `0063`) drops every record before it is created and clears the buffer when set. The drivers' own logs keep nothing and are cleared: the modem driver's rings (`0190`), the SCP's DRAM log and its saved copies (`0191`), block tag traces (`0192`), BTIF's packet rings (`0193`), bootprof events (`0194`), the display recorder (`0198`); each checks the switch under the lock its clearing takes before storing. The preloader's, LK's, ATF's and GenieZone's logs come from binaries r1metal does not build; while logging is off r1metal reads and copies none of them. Turning logging on starts from that moment, and the log notes which records are missing |

At every level, gen4m instructs the WiFi chip's firmware to keep no log (`EnableDbgLog` 0) at every power on; only an ioctl on `/dev/fw_log_wifi`, which nothing calls, turns it on. The chip still writes about 12.7 KB into its EMI ring at power on and 1.9 KB at power off, which the driver discards unread while no log node is open (module patch `0015`).

**Flash-time level.** `r1 flash` writes a file `flashed` into the ramdisk root with the lines `stamp N`, `logging on` and, if a key was given, `key KEY` with the OpenAI key ([OpenAI](../app/openai.md#the-key)). `r1 flash --log off` writes `logging off` and `--log debug` writes `logging debug`; each also adds its kernel parameter to the boot image's command line, `printk.silent=1` or `printk.debug=1` (`Logging::to_parameter`, named beside the switches in `r1_funcore::logs::kernel`). The parameter applies at every boot of that image until the app sets the switches: silence from the kernel's first line, with the buffer cleared when it is set; debug from the early parameters on, before the first debug record of the memory layout; a dynamic debug call site prints from dynamic debug's start, an early initcall. Process 1 sets the kernel's switch for off once `/sys` is mounted. The settings thread applies a flash's choice until its stamp is kept: it stores the choice with the settings and the stamp in `/data/.r1metal/interface/flash`, and passes the key to the `keys` thread. The stamp of a flash without a key is stored at its first boot; that of a flash that gave a key is owed until the `keys` thread has said that it kept the key (`Flash::stamps_to_keep`, `key::Report::is_flashed`, `Keeper::keep_flash_stamp`), so a flash whose key could not be kept is applied again at the next start, its logging included. From then on the screen's switch decides. A device without a data partition follows the flash alone.
