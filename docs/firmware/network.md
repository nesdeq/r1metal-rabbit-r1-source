# Network

The radio's core is powered only while some part of the firmware wants it, and the device is in a network only while a thread holds the network. With MOBILE DATA on, the modem's data connection stands in where WiFi is not to be had ([Mobile data](#mobile-data)). DNS goes to Cloudflare alone; a network's own resolver is asked one thing only, in a network of IPv6 alone, the prefix of its NAT64 ([Mobile data](#mobile-data)). Nothing waits for IPv6 but a connection or a question none of whose addresses answered while one had no route, for at most 4 s ([Connections and TLS](#connections-and-tls)). With USB MODEM on, a computer on the cable is lent the modem's connection, through a WireGuard tunnel alone where VPN is on ([Router](#router)). The drivers and the chip are described in [WiFi](../hardware/wifi.md), the modem in [Modem](../hardware/modem.md).

## The radio thread

One thread, `radio`, owns the core. It takes requests (`r1_funcore::wifi::radio::Request`) from five sources: the WiFi screen's network list (a listening pass, or a trial join that proves a chosen network), threads that hold the network, sleep, the console (`radio on`, `link on`, `link cell`), and the router, whose host has every stay routed ([The routed stay](#the-routed-stay)). Each round takes the requests that piled up (`Round::add`): of each kind only the last counts, holds are answered in turn, and releases are counted per stay. `Wants` then decides whether the core is powered, whether the device should be in a network, whether those who ask for it are refused, whether to join the default network, and what a trial join came to.

- A request is counted before it is sent; the nudge only wakes the thread to read the count.
- Holding and releasing interrupt nothing. Every other request (power, pass, trial join, link, the modem's network alone, routed stays, sleep) aborts a running scan or join at once (`Request::is_urgent`), and a join that one came to while it was set up gives way before its connect request goes out; the aborted work runs again afterwards if it is still wanted (`Preempt`).
- The console's `radio on`, `link on` and `link cell` go out by the number of the console's ask (`State::want_power`, `State::want_link`): a core that did not come on, a failed join or a lost link spends the wish, and the same verb given again asks anew.
- The core is powered through the driver ([WiFi](../hardware/wifi.md#drivers)). A separate thread, `radio power`, writes `/dev/wmtWifi` while the radio thread answers the driver's questions.
- A thread that can wait no more ends its stay and powers the core down in a last round (`Rounds::end`), and counts as off from then on (`State::is_off`): a hold is refused with `the radio's thread has ended`, and nothing of the radio keeps a suspend off.

## Scanning

The thread brings `wlan0` up and talks to the kernel over generic netlink (`wifi/nl80211.rs`, `wifi/scan.rs`). It looks up the `nl80211` family number and never assumes it.

- A scan without an SSID is passive; an active scan carries one empty SSID. `NL80211_ATTR_SCAN_FREQUENCIES` limits a scan to given channels.
- The end of a scan arrives on multicast group `scan`. `NL80211_CMD_GET_SCAN` returns each access point's address, frequency, signal and name, and how it lets a station in, read from its RSN element by the join's own reader (`rsn::choose`): by a password the join proves, by SAE or with the four way handshake, or by an offer no join here speaks, which the list bars and no join prefers. Results without address, frequency or signal are dropped, because band choice and ordering use the signal.
- A new request aborts a scan at once with `NL80211_CMD_ABORT_SCAN`, without waiting for the abort to complete. A scan refused with `EBUSY` waits for the running scan to end and is sent again. An end message counts for this scan only after the kernel has acknowledged its trigger (`scan::State`). A scan that has not ended after 10 s (`wifi::TIMEOUT`) fails and is aborted.
- The log records how many networks a scan found per band and how they authenticate; it never records network names.

**Listening pass.** The network list requests a pass by number. The thread powers the core, listens, powers the core down, and only then returns the pass number with the networks found: a frame drawn while the core powers down takes up to 14.2 ms instead of 5.0. Where a join follows in the same round, the pass is returned before the join begins, which over the modem may take as long as an attach (`Step::Tell`). During a WiFi stay the pass's scans also read the stay's link (`Association::serve`): a key the network renews meanwhile is confirmed in its time, and a loss read then ends the stay once the pass is over. A pass is two passive scans, first one channel, then all channels. The chip's first scan after power on dwells only about half a beacon interval per channel ([WiFi](../hardware/wifi.md#what-gen4m-does)), so it misses access points the second finds. A pass stops when the list closes or the device sleeps; the list requests it again after the device wakes. A pass aborted by another request resumes afterwards with a new scan. A pass never transmits.

**Trial join.** A network becomes known only after a join to it succeeds. The list requests a trial join by number, with the change that depends on it: a new network to remember with its typed password, or a known network to make the default. The thread powers the core, ends a WiFi stay that stands (its holders are notified; a stay over the modem goes on, [Mobile data](#mobile-data)), and joins as for the default network (`enter` in `wifi/radio/connect.rs`), but with this one network: kept place first, proof, connect request, handshake, then a DHCP lease or the kept lease. A trial carries no traffic (`join::Purpose::Trial`): IPv6 stays off on `wlan0`, no router is asked for its announcement, and the lease is kept for the next join but put on no interface, so the trial sets no route and takes nothing of a stay over the modem. It then disconnects, powers down, and returns the result (`LinkError::to_trial_error` in `r1_funcore::wifi::join`):

| How the join ended | Result shown in the list |
|---|---|
| No access point of the network found | `NOT HEARD` |
| On a network with a password: SAE proof failed, the access point disconnected the station, or the deadline passed | `WRONG PASSWORD` (an access point never reports a wrong password; it stops the handshake) |
| The same on an open network; or refused, no answer, or no supported security | `NOT LET IN` |
| Associated, but no address in time | `NO ADDRESS` |
| Core not powered, a scan or call failed, or the change names no network to join | `RADIO FAILED` |

After a successful trial, the main loop sends the change to the settings thread together with the place, so the next join scans one channel first. A trial join is interrupted and resumed like a scan, unless the list has closed or the device sleeps. A request for the default network waits until the trial ends, and the list is told how the trial ended before that join begins.

## Joining

The default network is the known network chosen most recently among those found (`r1_funcore::wifi::known`). Its 2.4 GHz access point is used if its signal is -70 dBm or better; otherwise its strongest access point is used ([Bands](#bands)). `r1_funcore::wifi::join` decides each step from the network's offer, the kernel's messages and the network's frames up to the keys; `wifi/association.rs` performs them.

| Step | How |
|---|---|
| Scanning | `.r1metal/wifi/place` keeps one place per known network, most recent join first: the network, its access point's frequency, and its frequency on the other band if one was found (`Places::plan`, `scan_places`). Each look is one scan, active on channels the rules allow (one empty SSID) and passive elsewhere. Order: (1) the last join's channel; (2) unless the most recently chosen network was found there, the channels of networks chosen after it, plus the first channel again if no known network was found on it; (3) while no known network is found, the other-band channels of those networks; (4) then both channels of every other known network. A 2.4 GHz access point below -70 dBm triggers one more scan on its network's other band, and the better access point is joined. With no places, or no known network found at any place, the thread scans all channels: actively where allowed, joining at once if the most recently chosen network answers on 2.4 GHz at -70 dBm or better, else passively on all channels. If no scan has run since power on, a one-channel listen comes first, so that the full scan is not the chip's first |
| Connect request | `NL80211_CMD_CONNECT` with SSID, BSSID, frequency and the station's RSN element, so the driver goes straight to authentication. The port stays closed until the station has keys. The request is sent on group `mlme` from the socket that owns the link (`NL80211_ATTR_SOCKET_OWNER`): only that socket receives the SAE request and the disconnect, and closing it ends the link |
| Security | Pairwise cipher CCMP is required; group cipher CCMP or TKIP. SAE where the network offers it with protected management frames (WPA3, or WPA3 alongside WPA2). Otherwise the four way handshake: over SHA-256 with protected frames where offered, over SHA-1 where offered, over SHA-256 without protection where SHA-1 is not offered |
| Password key, without SAE | PBKDF2-HMAC-SHA1, 4096 rounds (`wpa::ROUNDS`), 7 to 22 ms |
| Password element, for SAE | A P-256 point from the password and both MAC addresses. Hash-to-curve where the RSN extension element asks for it (two HKDF values mapped by simplified SWU, added, multiplied by a value from the addresses); otherwise hunting and pecking, at least 40 rounds of equal work. 6 to 27 ms. The last key or point is kept in memory and reused for the same network and addresses (`credential::derive`) |
| SAE | `r1_funcore::wifi::sae` sends a commit (scalar and element), reads the peer's, derives the key, sends a confirm and checks the peer's confirm; a wrong password shows up as a failed confirm. Frames go out with `NL80211_CMD_FRAME`. The thread also registers an unused action frame type, as gen4m asks ([WiFi](../hardware/wifi.md#what-gen4m-does)). An anti-clogging token is returned with the next commit |
| Handshake | EAPOL over a packet socket (`r1_funcore::wifi::wpa`), with the PSK or the SAE key: nonces, key derivation (HMAC-SHA1, or HMAC-SHA256 for SHA-256 networks and SAE), MIC checked and computed for each frame, RSN element and extension compared with the beacon's, group key unwrapped (for a TKIP group key the two MIC keys are swapped, as in wpa_supplicant). Message 2 carries the RSN element of the association request as the kernel reports it, because gen4m writes its own; frames are processed only after that report |
| Keys | `NL80211_CMD_NEW_KEY` for the pairwise key (then set as default for sending), the group key, and, with protected frames, the management group key, which is never set as default ([WiFi](../hardware/wifi.md#what-gen4m-does)) |
| Protected frames | Used where offered, required where the network requires them, as the station's RSN element states to the driver |
| Later frames | A repeated message 3 is answered without reinstalling the keys; a group key update is confirmed, and installed unless that key is the one in use, whose packet number a reinstall would set back (`wpa::Supplicant`) |
| Deadline | 10 s from the connect request to keys in use (`wifi::TIMEOUT`), 1 s where the modem stands in (`join::Limits`, [Mobile data](#mobile-data)); then the station disconnects and the join fails. A frame the crypto library cannot sign is not sent, and the join fails |
| Reach | Where the modem stands in, a stay's join ends only once the network reaches a resolver: with its address on the interface, the station asks all four of Cloudflare's resolver addresses for a TCP connection on port 853 at once (`wifi::reach`, `wifi/reach.rs`), and the first that completes proves the network; the connections are closed unused. No answer within 1 s, every address refused or without a route, or the link lost meanwhile fails the join, the station leaving the network. A network that takes a connection to that port and blocks what follows passes the proof. A join nothing stands in for proves no reach |

`r1_funcore::wifi::sae::point` derives the password element in the order the standard gives, with every choice between candidates masked. All curve and field arithmetic is AWS-LC's, through `aws-lc-sys`, the layer under `aws-lc-rs` (`crypto/curve.rs`), by the steps whose time follows no number: sums and differences under the prime by `BN_mod_add_quick` and `BN_mod_sub_quick`, products by Montgomery multiplication (`BN_mod_mul_montgomery`), powers by the library's constant-time exponentiation, and the map's 48 bytes brought under the prime by those sums and products of its pieces, never by the library's division. The tests check SAE value by value against IEEE 802.11-2020 Annex J.10 as wpa_supplicant's tests use it (looping element, commit, confirm key, PMK, PMKID), hash-to-curve against the same annex, the SWU map against AWS-LC's own hash-to-curve, and the handshake frame by frame against Python's `cryptography` for WPA2 with and without protected frames and after SAE.

## Bands

| On battery, channel 2 (20 MHz) and channel 48 (80 MHz) | 2.4 GHz | 5 GHz |
|---|---|---|
| Radio off | 81.5 mA | 79.4 mA |
| In the network, idle | 131.5 mA | 155.8 mA |
| During downloads | 134.1 mA | 156.6 mA |
| A 2 MB body | 359 to 439 ms | 132 to 165 ms |
| First rate | 65.0 Mbit/s | 292.5 to 390.0 Mbit/s |
| First scan to in the network, kept place | 205 to 318 ms | 178 to 313 ms |

A stay costs about 50 mA on 2.4 GHz and 76 mA on 5 GHz, whether it carries traffic or not; 5 GHz saves a quarter second per 2 MB. A stay that waits for a server longer than about a third of a second is cheaper on 2.4 GHz. So 2.4 GHz is preferred wherever its signal is -70 dBm or better (`LOW_POWER_FLOOR` in `r1_funcore::wifi::scan`); at that level, by the standard's receiver sensitivity table, a 20 MHz link still runs at over half its best rate. A weak 2.4 GHz access point has its network's 5 GHz channel scanned in the same join. After a stay on 5 GHz, before powering down, the thread scans the network's 2.4 GHz channel once (116 ms) and moves the place there if the signal is good enough.

## Addresses and leaving

- **MAC address.** Set before every join: the first six bytes of HMAC-SHA256 over the network's SSID, keyed with `.r1metal/wifi/secret`, with the locally administered bit set (`r1_funcore::wifi::station`). Each network always sees the same address, so its DHCP server recognises the device; different networks see different addresses.
- **Leaving.** `NL80211_CMD_DISCONNECT` with reason 3, the IPv4 address removed, the core powered down unless something else wants it. Every exit from a link the station may have an address in leaves it through one function, `leave` in `wifi/radio/mod.rs`, a join that fails after its address was asked for included; for a link the network ended itself it tells the network nothing and only takes the address off. Before a restart or power off the app makes the radio leave and waits for it, together with the settings and the logs, at most 10 s (`power::SHUTDOWN_TIMEOUT`); after that the device goes down anyway. The disconnect matters with protected management frames: an access point makes a station that vanished wait seconds when it comes back, while it asks whether the old association still stands, and takes one that disconnected in at once.
- **New hold.** A stay ends when its last holder releases it; the station disconnects and the core powers down. The next hold is a new join, which reuses the kept lease.
- **IPv4.** The firmware's own DHCP client runs over a packet socket. It sends DISCOVER with rapid commit (RFC 4039), takes the first OFFER, sends REQUEST, and sets address, netmask and router on the interface by ioctl; a NAK restarts with DISCOVER. An unanswered message is resent after 4 s, then after twice as long; the client gives up after 10 s (`Client::next_wait`), and where the modem stands in after the 4 s, as its first message would go again ([Mobile data](#mobile-data)). Leases are kept in memory per access point (`r1_funcore::net::dhcp::Leases`). A lease younger than its renewal time (the server's T1, else half the lease) is reapplied at the next join to that access point without any DHCP exchange. The client never requests a previous address (RFC 2131 INIT-REBOOT), because a server may not answer that. DNS servers in the lease are ignored. A lease is not renewed during a stay.
- **ARP** is the kernel's. Before every join it is told to ask a neighbour that did not answer again every 100 ms, the least RFC 8305 has two attempts lie apart, and 10 times in all, through the 1 s a backed join's proof of reach gets (`r1_funcore::net::arp`, applied by `sys::iface::write_arp`). The kernel's own are 1 s and 3 times, which leave a proof of reach no second asking, and Rabbit's tree asks no sooner than every 500 ms whatever is written (patch `0209`).
- **IPv6** is the kernel's, configured as `r1_funcore::net::ipv6` defines and applied by `sys::iface::write_ipv6`, for a stay on `wlan0` and the modem's `ccmniN` alike; a trial join keeps it off ([Scanning](#scanning)):

| Setting | Why |
|---|---|
| `disable_ipv6` set to 1, then 0, before every join for a stay | The kernel keeps addresses, routes and neighbours across stays and would use another network's; stale entries also slow the first connection |
| A stay's station sends its own router solicitation, with its link-layer address, once keys are in use | The kernel solicits when the link comes up, before keys, then at 4, 12, 28 and 60 s, and not at all on a link it knows. A router answers a unicast solicitation at once; a multicast answer waits for a beacon |
| `dad_transmits` 0 | Duplicate address detection takes a second, longer than most stays. RFC 4862 allows skipping it, and the addresses derive from a random MAC address or are random |
| `use_tempaddr` 2, `router_solicitation_delay` 0 | Temporary addresses created and preferred; no delay before the kernel's own solicitation |

## Holding the network

`Radio::online` gives a thread an `Online`, its way to the network. What a part asks of OpenAI holds the network through the account, which keeps one ([OpenAI](../app/openai.md#account)); the Pokédex keeps its own for a name typed, Signal its own for its service, which its stay and each transfer of an attachment hold, and the calls' part its own for a call ([Calls](../app/calls.md#power)); the browser holds through the account for the pages it fetches itself too ([Interface](../app/interface.md#web)).

- `Online::hold` returns once the device is in a network, or returns why it is not (`Fault::Offline`). The returned `Hold` keeps the device in the network until it is dropped.
- `Online::keep` holds the network into an `Option<Hold>` the caller keeps. A hold whose stay is still current is reused; a hold whose stay has ended is dropped and a new one taken (`NetworkDown::is_raised`). A thread with a series of jobs thus runs them in one stay. A voiced job's turn thread reuses the stay it holds by the same rule (`voiced::Worker::DOWN`), and so does the hold it keeps while a recording runs: one whose stay ended meanwhile is taken anew at once.
- The radio thread counts the holders of each stay. A release lowers only its own stay's count. A stay ends when nobody holds it, nobody waits for it and the console has not asked for a link (`Wants::should_link`); when the network is lost; or when the device sleeps.
- When a stay ends, every connection made during it ends too: every wait on a connection also watches the stay's end (`Hold::down`, a `NetworkDown`, which holders and connections wait on and look at and only the radio's thread raises), and so does a wait for an asking another has under way of what all ask in turn, a DNS query, a stay's NAT64 search and the first time check (`base::handoff::Turns`, `dial::await_turn`); the connections the stay left in the account's pool are dropped as soon as the main loop hears from the radio (`Account::drop_ended_connections`).
- A hold is shared with a job of another thread beside its holder's (`Hold::share`): the radio counts it once, and the stay stands until both have let go of it.
- While the device sleeps, a hold is refused at once. Exceptions: while the news editor has an edition to make, while Signal fetches for its alarm, answers what that brought in auto mode, has a request on its way over its open socket, has an attachment to carry or links the account the phone sent, while the reader waits for the cost of a passage, while the conversation has a turn or a recollection in progress, and while the router serves a computer whose link is up ([Sleep and clock](sleep.md), `app::Debts`).
- Where no network is known and the modem takes no asks, or the console asked for the modem's network alone and the modem takes no asks, a hold is refused at once and the console's wish for a link is spent, so the core comes on for neither (`Wants::take_refusal`); the console refuses `link on` and `link cell` then itself ([Console](console.md#verbs)).
- A hold has the clocks checked beside it, as [Sleep and clock](sleep.md#clock) tells (`Timing::hold_hook`, handed to `Radio::start`).

## Mobile data

With MOBILE DATA on, the `ccci_mdinit` thread keeps the modem booted, and its attach between stays as [Modem](../hardware/modem.md#in-r1metal) tells (why, and at what cost: [Cell](cell.md)). The radio thread is handed the modem's side for the radio (`cell::Cellular`), and each round notes whether the modem takes asks: running, its SIM ready, and no failed connection being waited out, counted in boot time, which runs on through a sleep (`modem::State::is_usable`, `Rounds::set_ways`). The console asks the same before it takes `link cell`.

- WiFi comes first while a known network is in reach, the modem first while none is (`Rounds::can_join_wifi`). With the modem taking asks, a join looks for the known networks at their kept places alone, never on every channel (`Rounds::is_look_narrow`, `search::find_known`); a network not heard there, a failed join or a core that does not come on goes to the modem in the same round, the core powered down first (`Step::CellJoin`). With no network known, or none with a kept place (`Places::holds_known`, `Rounds::set_ways`), the core never comes on for a stay.
- A backed join is short and proved (`join::Limits::BACKED`, `Rounds::join_limits`): 1 s from its beginning to keys in use, an address for as long as its first asking stands (4 s, which a server that probes the address for 3 s before it lends it still meets), and 1 s for a resolver's answer ([Joining](#joining)). Each step that runs out fails the join, and the modem's connection is asked for in the same round.
- A known network that was heard and did not serve, one that did not take the station in, lent no address or reached no resolver, is passed over for 15 min, as long as the modem keeps an attach (`Rounds::pass_over`, `to_joinable`): no look and no join is made for it while the modem takes asks, and the log tells `wifi: "NAME" is passed over for 15 min, the modem standing in`. A trial join that proves it on the WiFi list ends that at once.
- The look that tells whether WiFi is to be had is made when nobody waits. A WiFi join that failed has the next stays go to the modem at once, with no look and no power for the core before them. At the end of each stay over the modem the thread powers the core, looks for the known networks it may join at their kept places (`Step::Look`, `search::hear_known`), powers it down and keeps the word: one heard has the next stay look for WiFi first, none has it go to the modem. A look that gave way to another request is owed, as the device goes to rest too, and is made in the next round nobody asks for a network in. A hold that comes while the look runs waits for its end.
- A modem's join that fails where WiFi was not tried has WiFi tried in the same round, on every channel and with a join's whole times, as nothing stands in any more (`Rounds::fail_join`).
- The console's `link cell` passes WiFi over (`Request::Cell`): a WiFi stay that stands ends and the core goes off, and every stay goes over the modem until `link on`, `link off` or a sleep.
- The ask waits for the modem's answer and gives way to an urgent request as a scan does (`Cellular::join`); an ask taken back has the modem drop what it set up for it, and a connection granted after is let go of.
- A stay over the modem ends as a WiFi stay does, its `NetworkDown` raised; the modem tells a lost connection through a descriptor the thread watches, and leaving it hands it back (`Cellular::release`). A stay over the modem looks for no low band, and a trial join on the WiFi list leaves it standing and takes none of its traffic.
- DNS, TLS and connections are the same over both: the default route is over `ccmniN` while the stay stands.
- The APN a connection takes is chosen in [Cell](cell.md#choices). The modem's thread hands the radio the connection's interface, `ccmniN` (`modem::Step::Grant`), and where the network gives a connection of IPv6 alone (an operator's IPv6 APN), the network's DNS servers with it; the stay's `NetworkDown` carries both. The first connection or question of such a stay asks the servers over UDP for the AAAA records of `ipv4only.arpa`, under a number drawn at random for the question that the answer must carry (RFC 5452), whose IPv4 addresses (`192.0.0.170`, `192.0.0.171`) the network's DNS64 writes into its NAT64's prefix, and reads the prefix out at the place each length of prefix puts them (RFC 7050, RFC 6052, `dns::nat64::parse_prefix`). The resolver's answer, a prefix or that it knows of none, counts for the rest of the stay; a search that got no answer, or only answers of a resolver that could not say, counts for the connections that waited for it, and the next connection searches again, as a DNS query that failed is asked again by the next lookup ([DNS](#dns)). A holder that wants the prefix while it is asked for waits for that asking, or for its own stay's end (`dns::nat64::Search`). From then on every IPv4 address a connection or a question is given becomes the IPv6 address the NAT64 reaches it at, where it stood in the order (`dns::nat64::to_reachable`, in `dial::connect` and `dial::exchange`); without a prefix the IPv4 addresses are passed over. The log tells `names: the network's NAT64 is 64:ff9b::/96, as 2001:db8::53 told it in 41 ms`, `names: the network has no NAT64, as 2001:db8::53 told in 41 ms, so IPv4 addresses are passed over`, or why none was found.

## Router

With `USB MODEM` on ([Interface](../app/interface.md#mobile-data)), the R1 is a modem for one computer on its cable: the computer gets one IPv4 address, and its packets leave over the modem's connection, translated to the connection's address; with `VPN` on they leave through a WireGuard tunnel and by no other way. The R1's own traffic goes on beside the computer's, outside the tunnel. One thread, `router` (`router/mod.rs`), forwards every packet: it reads a packet, hands it to funcore's `domain::router::Machine`, and does each step that returns (`router::Step`), one effect each. The kernel filters, tracks and forwards nothing ([Kernel](../hardware/kernel.md#kernel-facts-the-firmware-is-built-around)).

| Packets of | Reach the forwarder by | Leave, `VPN` off | Leave, `VPN` on |
|---|---|---|---|
| The computer | a packet socket on the gadget's network interface, as Ethernet frames | the modem's connection | the tunnel |
| The R1's own IPv4 | the TUN interface `tun0`, which the default route is over | the modem's connection | the modem's connection |
| The R1's own IPv6 | never: the kernel sends them over `ccmniN` | | |

### The computer's link

- The gadget shows a host a network adapter (CDC NCM, function `ncm.usb0`, [Console](console.md)); `usb::start` gives its two ends hardware addresses made of the gadget's serial number, a station's and set locally (`hw::usb::to_hardware_fields`), so a host meets the same adapter at every start, and binds the gadget without the function where the controller refuses it. The interface's name is read from the function's `ifname`.
- The interface has no address and IPv6 off (`ipv6::OFF_WRITES`): the kernel's stack never sees the computer. The forwarder answers the computer's ARP for the router's address itself (`arp::answer`) and lends by DHCP (`dhcp::Server`): `192.168.42.2` of the block `192.168.42.0/30`, the router and the resolver at `192.168.42.1`, a lease without end, and the largest packet the computer's way carries (option 26: the modem's, or the tunnel's where a config is kept, whichever is less). It lends once the stay's way is open, so a computer with a lease has a way.
- The link counts as up while the interface runs (`IFF_RUNNING`, read at each word of the kernel's link news, `iface::route_events`): a wall charger, and a host that takes no notice of the adapter, hold nothing.

### The routed stay

- While the router is wanted and the computer's link is up, the forwarder holds the network (`Online::hold`), and the main loop tells the radio that stays are routed (`Router::is_routing`, `Radio::want_route`, `Request::Route`): every stay then goes over the modem alone, whatever WiFi is in reach, and is set up routed; a stay that stands and is not ends at the change, as does a routed one once nothing is routed any more, and its holders ask anew (`Rounds::is_routed`).
- A routed stay is the modem's connection with its IPv4 taken off the kernel (`cell::Link::route`, `cell/link.rs`): once the modem's thread has set `ccmniN` up, the radio's thread reads the interface's address and MTU, gives `tun0` the address `192.0.0.2` (RFC 7335) with that MTU, has `ccmniN` merge no TCP segments (`iface::set_merging`, the kernel's generic receive offload, which the modem's driver hands every packet to: a merged packet is larger than the computer's link carries), takes the connection's address off `ccmniN`, which drops the default route over it, and puts the default route over `tun0`. The stay's `NetworkDown` carries what was taken off (`NetworkDown::routed`, `cell::link::Routed`). With no local address the kernel answers nothing that comes for the connection's address: no reset, no refusal. The stay's end takes `tun0`'s address off again and has `ccmniN` merge segments again, for the kernel's own connections (`Link::unroute`).
- The forwarder opens a packet socket on `ccmniN` for the stay it holds and forwards for it until the stay ends, whoever else holds it; a hold it let go of, the computer gone, leaves the R1's own packets their way until then.
- The main loop wants the router only while `USB MODEM` and `MODEM` are both on and the modem takes asks for a connection (`Settings::lends_modem`, `Modem::is_usable`, the word the radio's rounds go by): with the modem off, without a SIM or its PIN, or waiting out a failed connection, nothing is routed, the device's own stays go their usual ways, and `USB MODEM`'s line says `MODEM NOT READY`.
- A stay refused, the modem not ready or its connection failed, is asked for anew by the computer's next frame, no sooner than 4 s on, the time after which a host that waits for its lease asks again (RFC 2131, `ASK_AGAIN`); a link that comes up, a setting changed or a stay lost asks at once.
- Asleep, the router's debt keeps the radio from its rest while a computer's link is up (`app::Debts`), and a suspend waits for it (`Parts::is_quiet`).

### Translation

`net::nat` keeps one table of flows for the computer and the R1 itself, each by its way out (RFC 4787, RFC 5382, RFC 5508):

- A flow keeps its own port where no flow of its way to the same far end has it, else takes the next free one of 1024 to 65535 (RFC 6056); a way holds 64512 flows of a protocol at the most. A packet from outside passes only as the answer of a flow, by address and port; anything else is dropped, for the computer and the R1 alike.
- A flow nothing passes over goes after 5 min for UDP, 2 h 4 min for a TCP connection both sides opened and 4 min before and after, 60 s for an echo; the table is swept every 60 s. A TCP flow begins only with the segment that asks for a connection.
- ICMP errors pass both ways, their quoted packet rewritten; a TCP connection's largest segment is clamped to its way's packets; a packet too large for its way that may not be cut is answered with the way's size, one that may is cut; the pieces of a packet follow their first.
- A flow whose way is no longer the one its packets take is dropped, and a change of `VPN` drops every flow of the computer's, so none goes on along the old way.

### The tunnel

- A config is the text `wg-quick` takes (`wireguard::config::Config::parse`): one interface, one peer. It is read from a QR code in the `TUNNEL` window ([Interface](../app/interface.md#mobile-data)) or handed over the console behind the debug shell's gate (`tunnel BASE64`, [Console](console.md#debug-shell)), and kept in `.r1metal/router/tunnel` in the safe ([Storage](storage.md#layout)); one config is kept, and a new one takes its place. A config is refused that has no IPv4 `Address`, no IPv4 `DNS`, a peer that does not take every address (`AllowedIPs` without `0.0.0.0/0`), an `MTU` under 576, or an address or resolver in the computer's block (`router::read_config`, `config::Flaw`).
- `net::wireguard` is the side that begins: the handshake (Noise IKpsk2 over X25519, ChaCha20-Poly1305 and BLAKE2s, `noise.rs`), the cookie a peer under load answers with, data messages with their counter and a window of 8192 counters against replays (RFC 6479), and one peer's sessions and timers as the whitepaper sets them (`peer.rs`): a new session after 120 s, none used past 180 s, a handshake tried again every 5 s for 90 s, an empty message 10 s after a packet came that nothing was sent behind, a new handshake 15 s after one went that nothing answered, and the config's `PersistentKeepalive`. X25519 and the two ciphers are AWS-LC's (`crypto/wireguard.rs`); BLAKE2s is funcore's (`crypto::blake2s`). A packet for a tunnel with no session is dropped and a session asked for.
- The tunnel's datagrams go over an ordinary UDP socket: they are the R1's own traffic, and leave through `tun0` and the translation like any. The peer's name is looked up by the firmware's resolver, outside the tunnel, on a thread beside the forwarder (`router names`); a peer not found or not reached is looked for again by the computer's packets, no sooner than 5 s on, and one that answered no handshake for 90 s is looked up anew.
- The tunnel carries packets of 1384 bytes, of the config's `MTU`, or of the connection's less 80 (IPv6's head, UDP's, a data message's and its tag), whichever is least (`Config::mtu_within`).
- With `VPN` on, `Machine::path` gives the computer's packets the tunnel's way whatever the tunnel's state: no config kept, the peer not found, no session yet, a session gone silent, all drop them. Nothing falls back to the modem's connection.

### Lookups

The computer's resolver is the router's address, and the translation turns what it sends there to port 53, over UDP or TCP, to the resolver of its way (`Nat::route`); a computer set to another resolver reaches it as any address.

- `VPN` on: to the config's `DNS`, through the tunnel.
- `VPN` off: to the relay on the R1 itself (thread `relay`, `router/relay.rs`), a UDP socket and a TCP listener on `192.0.0.2`, port 53, which stands while the forwarder serves a computer without the tunnel, under a share of its hold. `dns::Relay` passes each question on whole, whatever it asks for, under a number of its own and padded to a block of 128 bytes (RFC 8467), over one connection to Cloudflare by DNS over TLS, made at the first question and kept until the resolver closes it or the stay ends, and fits each answer to its asker: whole over TCP, and over UDP cut to its question and marked as cut where it is longer than the asker takes (512 bytes, or what the question's options name, RFC 6891), which sends the asker to TCP. An asker that sent no options gets none back. Of the computer's connections over TCP it keeps 128 at the most, as many as Linux 4.19 lets wait for a listener, and past that the oldest goes for a new one (`dns::Streams`). The relay never serves while `VPN` is on: its connection is the R1's own and leaves outside the tunnel.
- The log tells no name a computer asks for: the address the relay reached the resolver at with its times (`dns::to_relay_line`), and as the connection ends `names: the relay's connection ended, 11 of 12 questions answered`.

### A network of IPv6 alone

Where the modem's connection has no IPv4 address, the forwarder translates (`net::siit`, RFC 7915, as a 464XLAT client does, RFC 6877): flows leave from `192.0.0.1` (RFC 7335), and each packet becomes an IPv6 one from an address of the connection's network under an interface number drawn at random, which the kernel does not hold, to the far end's address behind the network's NAT64 ([Mobile data](#mobile-data)); what comes back for that address becomes IPv4 again. A thread beside the forwarder (`router translation`) waits for the connection's global address and asks for the NAT64's prefix (`dial::find_translation`); the way opens once both are known, 20 bytes narrower than the connection's, and a network that tells no NAT64 gives the computer no way.

### The log

`router: a host's link is up`, `router: the stay is routed, packets of 1500 bytes`, and how the router stands at each change (`router::Standing::to_log_line`): `router: the host's packets leave over the modem's connection`, `... through the tunnel`, `router: the tunnel is not up, the host's packets are dropped`, `router: no config of a tunnel is kept, the host's packets are dropped`. No line tells a key, and a config handed over is logged as `tunnel (given)`.

## DNS

DNS over TLS (RFC 7858) to Cloudflare only: `one.one.one.one`, port 853, at `2606:4700:4700::1111`, `1.1.1.1`, `2606:4700:4700::1001` and `1.0.0.1`, which validate DNSSEC and filter nothing. A network that blocks port 853 resolves nothing.

- The A and AAAA questions for a name go out together over one connection, each padded to a multiple of 128 bytes (RFC 7830, RFC 8467). Questions for many names go out together the same way (`names::resolve_all`), each name once however it is written (`dns::Lookup`), matched to answers by their IDs.
- Answers are cached by name and shared by every thread. A name is cached for the shorter TTL of its answers that carry addresses; a TTL with its top bit set counts as 0 (RFC 2181, section 8). An IP address needs no lookup, nor does a cached name. Results are filled in per name (`dns::Lookup`).
- Addresses are returned in connection order: IPv6 first, then alternating families (RFC 8305).
- One query runs at a time (`Resolver::resolve`, `dns::State`), so that a name several threads want is asked for once, over one connection. A thread that needs a name meanwhile waits for that query, or for its own stay's end, and then reads the cache. Threads of the query's stay that waited on it get its error where it failed and do not retry; a thread of another stay, and one that comes after it, asks for itself.
- Cloudflare speaks TLS 1.3, and the device sends no early data, so a query on a new connection costs three round trips. The relay of a computer's lookups reaches the resolver by the same function (`names::reach`), and keeps its connection ([Lookups](#lookups)).
- While a query runs and the firmware logs ([Logs](logs.md#the-logging-switch)), a packet socket (`AF_PACKET`, every protocol) is handed every packet the device sends and receives, and after the query the log tells the TCP segments to and from port 853 among them, in order, by address (`names::PacketSocket`, `r1_funcore::net::watch`): each segment's direction and flags as tcpdump writes them and the bytes it carried, and of one that came its TTL or hop limit, IPv4 identification and window, as in `names: segments of 1.1.1.1 port 853: >S, <S. ttl 57 id 0 win 65535, >P. 517, <R ttl 249 id 4321 win 0`. A segment the server sent and one a middlebox made in its name differ in the hops they crossed. The socket lives only as long as the query and holds at most 4 MiB (`watch::BUFFER_BYTES`).

## Connections and TLS

`dial::connect` tries the addresses in order and returns the first connection that succeeds (RFC 8305, `r1_funcore::net::race`). Each attempt starts 250 ms after the previous one, or at once when the previous one failed. Attempts are non-blocking sockets polled together, so a family without a route costs nothing. `TCP_NODELAY` is set. Only when no address answered and some had no route does it wait, at most 4 s (RFC 4861), for a global IPv6 address on the stay's interface (`wlan0`, or the modem's `ccmniN`) that has finished duplicate detection, then retry those addresses. `dial::exchange`, a question over UDP to addresses in turn, is raced the same way by the same driver (`dial::race`): an address that refuses the question (an ICMP port unreachable) has failed as a refused connection has, and once every address has refused the exchange ends. Every read and write fails after 10 s without progress and at once when the stay ends; `Stream::set_timeout` gives a slow server longer. A connection that paused sends on at the pace it had: process 1 writes `tcp_slow_start_after_idle` 0 at its start (`r1_funcore::net::tcp`, `sys::write_tcp`), where the kernel's own 1 has a connection that sends again after a pause longer than its retransmission timeout begin slowly anew.

TLS is `rustls` 0.23 with `aws-lc-rs` as its only crypto provider. The first key share offered is X25519 with ML-KEM-768, with plain X25519 beside it. Four client configurations live for the life of the process, one for each purpose (`r1_funcore::net::tls::Purpose`, which says what each offers and trusts), and each resumes sessions with servers it has met: DNS, HTTP (ALPN `http/1.1`, `http::ALPN`) and a call's relay or calling server reached over a stream (`Purpose::Relay`, no ALPN) trust Mozilla's root certificates, from `webpki-roots`, compiled in, over TLS 1.3 and 1.2; Signal's hosts, its CDNs `cdn.signal.org`, `cdn2.signal.org` and `cdn3.signal.org` among them, are reached under `Purpose::Signal` whoever connects (`signal::service::to_purpose`), and so are the calling server's join and peeks (`web::ask_request`), over TLS 1.3 only, trusting Signal's two roots alone and none of Mozilla's ([Signal](../app/signal.md#the-service)). Seeding the random generator takes about a third of a second and runs on its own thread, `entropy`, when the radio is first powered. Certificate validity is checked against the device clock, which the first time check since the start sets before a hold's TLS connections where the time service answers; one that did not still ends the holds' wait, and their connections go on by the clock as it stands ([Sleep and clock](sleep.md#clock)). No revocation checks, no client certificates.

## HTTP and WebSocket

- **HTTP/1.1** (RFC 9112), always under TLS: `r1_funcore::codec::http` parses URLs (`https` and `wss` only; `http`, `ws` and every other scheme are refused; names or addresses, IPv6 in brackets; port; path), writes requests, parses response heads, frames bodies (content length, chunked, until close, none) and decodes chunks. `web::ask` sends a request and returns the head and a body reader that buffers at most one read; `web::send` and `web::answer` are its two halves. `web::ask_once` asks one request on a connection of its own and closes it whatever came of the answer: the Pokédex's, a feed's, the browser's for a page and the place service's. `web::ask_request` asks a `signal::service::Request` so, under `Purpose::Signal`, and takes its body as far as the request lets it: Signal's requests to the storage service, the groups server and a CDN, and a call's to the calling server ([Calls](../app/calls.md#group-calls)). `Answer::read_checked` reads a body whole, its asker's check told its length after each read, which refuses one too large: an answer of OpenAI's and one of Signal's. `Answer::read_document` reads one under the limits of a fetched document, its size and its time (`net::fetch::check_read`): a feed's, a page's, the Pokédex's. `web::fetch` asks for a document on a connection of its own and gives the address its answer sends the asker on to or the document read so, for a feed and the browser's page alike (`net::fetch::Fetched`). 1xx responses are skipped. A truncated body is an error, including a TLS close without close_notify. `web::reach` resolves the host itself; `web::connect` takes resolved addresses; both put the TLS of the purpose they are given on every connection (`tls::Stream`, which has no other kind). `Head::redirect_location` and `Target::resolve` compute a redirect target, an `https` one or none; `web::ask` follows no redirects. No decompression (none is requested), no chunked uploads.
- **Connection reuse.** `Head::keeps_alive` returns whether the server keeps the connection open (RFC 9112, section 9.3: no `Connection: close`, and an HTTP/1.0 response only with `keep-alive`). `Framing::is_reusable` returns whether a fully read response with nothing after it leaves the connection usable; `Answer::is_reusable` calls it. `Pool` (`net/pool.rs`) keeps such connections under the stay each was made in (`Stream::network_down`) and per server (`Target::is_same_server`: host and port). A request in the same stay to the same server takes a pooled connection that the server has neither closed nor written to since; records that carry no data, a TLS 1.3 session ticket a server sends after the greeting among them, are taken in on the way (`Stream::is_ready`); connections left by an ended stay are dropped as soon as the main loop hears from the radio (`Pool::drop_ended`), without TLS's closing word, since the network under them is gone; a lookup drops them too, so none is handed out before then. `openai::Account` keeps one pool for all OpenAI requests ([OpenAI](../app/openai.md#account)).
- **WebSocket** (RFC 6455): `r1_funcore::net::websocket` writes the opening handshake with a 16-byte random key, checks the response (status, headers, the SHA-1 accept value), masks every frame with fresh random bytes, and parses the server's frames into text (UTF-8), binary, continuation, ping, pong and close. `websocket::Socket` sends and receives whole messages, answers pings, and handles close as funcore's `websocket::Action` defines; a message over 1 MiB is refused. `Socket::reach` reaches the server, opens the socket and sets how long the server is given (`Stream::set_timeout`). `Socket::next_message` returns the next message of the kind its caller takes, passing over any other, waiting for it or returning what has arrived without blocking (`websocket::Incoming`), where a TLS record that carries no data is nothing that has arrived. No extensions.

## STUN, ICE, TURN and RTP

What carries a call's packets. How a call uses each is in [Calls](../app/calls.md#the-way); its keys, streams and rates are the call's. Each is a value of funcore's that takes what came with the time and gives its steps one at a time; the `calls` thread does them (`crates/impshell/src/calls/`): a UDP socket bound on an address of the stay, any port, or a TCP stream begun without blocking, from the address the kernel picks, under TLS of `Purpose::Relay` where a server is named (`calls/stream.rs`), its segments sent as they come (`TCP_NODELAY`). A stream's write goes whole or, while earlier bytes still wait for the socket, not at all, as a link drops a datagram.

- **STUN** (`net::stun`, RFC 8489): messages with the attributes ICE and TURN use; a received one checked for its fingerprint and its integrity (HMAC-SHA1, or HMAC-SHA256 where a TURN server lists it); a request over UDP sent again from an RTO of 500 ms, 7 times in all, and one on a stream sent once and waited for 39.5 s; messages on a stream behind a 2-byte length (RFC 4571, as ICE over TCP frames them, RFC 6544), or toward a TURN server as STUN and ChannelData (RFC 8656, 12). A server's URI (RFC 7064, 7065, `stun::Uri`): `stun` and `turn` over UDP, or TCP with `?transport=tcp`, `stuns` and `turns` over TLS, at ports 3478 and 5349 unless named. Its HMAC-SHA1, MD5 and SHA-256 are AWS-LC's (`net::stun::Crypto`, `crypto/stun.rs`).
- **ICE** (`net::ice::Agent`, RFC 8445): a full agent of either role toward one far side or several that share its credentials, sockets and candidates, each by a number its owner gives it, with trickle (RFC 8838) and consent freshness (RFC 7675).
  - Its user fragment and password are 4 and 22 letters and digits drawn from random bytes; a far side's are taken at 4 to 256 and 22 to 256 characters (RFC 8839).
  - Candidates: a host candidate on a UDP socket of each address it is given, IPv6 above IPv4 (RFC 8421); an active TCP candidate on each, told to nobody, which pairs with a server's passive ones (RFC 6544); server-reflexive ones of STUN servers and of UDP relays; relayed ones, an allocation of each family on each relay; peer-reflexive ones as checks find them. Of a far side's candidate lines a TCP one is taken where it is passive; a server named by its addresses (`Agent::far_server`) stands as host candidates, its TCP and TLS ones passive, TLS checked by its name. An agent made relayed opens no host socket and uses and tells relayed candidates alone (`is_relayed`).
  - Checks go one every Ta, 50 ms (RFC 8445, 14.2), triggered ones first, the far sides in turn; a role conflict is settled by tie-breakers of 8 random bytes. A request without a fingerprint is no STUN; one without a user name or integrity is answered 400, one of a wrong user fragment or integrity 401.
  - The controlling side nominates its best valid pair, waiting up to 3 s after the first for a better one, and nominates again where a better one succeeds later, each nominating check carrying USE-CANDIDATE and libwebrtc's NOMINATION (0xC001) with its count; the controlled side takes either, the latest nomination winning.
  - Consent is asked on the selected pair every 4 to 6 s; 30 s without an answer fail the pair, the far side turning `Disconnected`, and media goes only under consent. A far side fails once nothing was left to check toward it for 30 s.
  - At the most 100 pairs, 100 candidates of this side's and of the far sides' together, 200 checks and 100 far sides (RFC 8445, 6.1.2.5); a server-reflexive binding is kept up by a Binding request every 15 s while no pair is selected.
  - The log: `ice: side 1 connected, 4 pairs` (`connecting`, `connected`, `disconnected, consent lost`, `failed`), `ice: side 1 media over udp from host to srflx`, `ice: side 1 no pair selected`, `ice: relay over tls failed: refused 401` (or `no answer`, `credential run out`, `allocation lost`, `integrity broken`), `ice: relay over tcp answered 400, passed over: not sealed` (an answer passed over by its code, or `a success`, and why: `not sealed`, `integrity broken`, `a downgrade`; told again for a request only where the reason changes) and `ice: a host socket was not opened`.
- **TURN** (`net::turn`, RFC 8656) as a client over UDP, TCP and TLS: a relayed address allocated under the long-term credential (realm and nonce; SHA-256 over MD5 where the server lists both, MESSAGE-INTEGRITY-SHA256 where it lists algorithms, USERHASH where it asks for anonymity), lasting 600 s where the server tells none and refreshed a minute before it runs out; a permission of 300 s for each far address a live pair of the relay's candidate has, 100 at the most; a channel (0x4000 to 0x4FFF, 600 s, kept from reuse 300 s after) for each pair a far side selected through the relay, Send indications where a channel is refused; a redirect followed where it is signed, to 3 servers at the most; closed by a Refresh of no lifetime. The Allocate asks for an IPv6 relayed address by REQUESTED-ADDRESS-FAMILY and for an IPv4 one without it, a server's default (RFC 8656, 7.2), as libwebrtc asks, since a server without RFC 6156 refuses the attribute. Of the answers to a request under the credential, the integrity of a success and of a redirect alone is checked, and any other error is taken by its code without one, as libwebrtc takes them (`StunRequestManager::CheckResponse`): a 400 without integrity is a refusal there, libwebrtc's rule, where RFC 8489, 9.2.5 has a client pass over a 400 without integrity to any request. Passed over as if never received, the request waiting on (RFC 8489, 9.2.5, `turn::Discard`), are an answer whose nonce asks for password algorithms it does not list, a 400 without integrity to a request without the credential, the RFC's rule kept for such a request alone, and over UDP a success or a redirect whose integrity is missing or does not hold, which over a stream ends the allocation at once; a 438 whose nonce asks for algorithms it does not list is not asked again.
- **RTP** (`net::rtp`, RFC 3550), a call's one transport for RTP and RTCP, ICE's datagrams told apart from them by their first byte (RFC 7983), tied by `rtp::session::Session`:
  - Header extensions in the one-byte form, or the two-byte form where an element is longer than 16 bytes (RFC 8285): the transport-wide sequence number, video orientation (3GPP TS 26.114, 7.4.5: the quarter turns, the flip and the back camera), audio level (RFC 6464), the dependency descriptor (the AV1 RTP specification, appendix A.8) and the video layers allocation (webrtc.org's video-layers-allocation00). Payloads of VP8 (RFC 7741), RED (RFC 2198, its primary block taken) and RTX (RFC 4588).
  - SRTP and SRTCP over AES-GCM (RFC 7714), `AEAD_AES_128_GCM` or `AEAD_AES_256_GCM` by the master key's length; the session keys by RFC 3711's key derivation in AES counter mode, the 12-byte master salt filled to 14 as the calling server and libsrtp fill it; a window of 8192 counters against replays for each stream (RFC 6479, `net::window`, the tunnel's too), a far stream's state made as its first packet opens. AES-GCM and the AES block are AWS-LC's (`net::rtp::Crypto`, `crypto/rtp.rs`).
  - RTCP (RFC 3550, 4585, 5104, 5506) read: reports, NACK, PLI, FIR, transport-wide feedback (draft-holmer-rmcat-transport-wide-cc-extensions-01) and REMB. Written: sender and receiver reports each second with video, each 5 s for audio alone, the first after half of one and each spread over half to one and a half; transport-wide feedback each 100 ms for every packet that carried a number; NACKs looked at each 20 ms, a missing video packet asked at once and again a round trip and a tenth later, given up after 10 tries or 3 s, 250 a stream at the most; a PLI where a stream wants a key frame, asked again each 200 ms until a key frame is handed over, none while a key frame's packets came within the last 200 ms or the stream has been silent 5 s (`Assembler::needs_key`, libwebrtc's `video_receive_stream2.cc`). Each but the reports goes in a datagram of its own.
  - Video frames are put together from their packets as libwebrtc's packet buffer and frame buffer put them together in outline (2048 packets, 100 frames waiting): by VP8's picture id, by sequence number, or by the dependency descriptor. A key frame is wanted where a frame refers to what never comes, a delta frame comes before any key frame, 3 s pass without a frame to hand while packets come, or a frame does not decode.
  - Sent video is kept 3 s, 750,000 bytes at the most, to be sent again as RTX for a NACK, a packet no sooner again than a round trip after.
  - The send rate from transport-wide feedback, as goog_cc reckons it in outline (draft-ietf-rmcat-gcc-02, `rtp::estimate`): a delay-based estimate by groups of arrivals, a trendline filter and an over-use detector driving AIMD on the acknowledged throughput, under a loss-based estimate that grows 8 % a second under 2 % of loss and cuts by half the loss over 10 %; feedback silent 3 s while packets go takes the rate to 0.8 of itself each second, down to 5 kbit/s; a REMB caps it. The pacer (`rtp::pacer`, libwebrtc's): audio and data at once, then what is sent again, then video, at 2.5 times the target until feedback comes and 1.1 times after, in bursts of 40 ms, its queue drained within 2 s; a key frame's first packet lets go of the video queued before it, and a frame is refused while the queue would take longer than 2 s.

## Limits

- No PMK caching: every join proves the password again.
- No downgrade protection: a network offering WPA2 and WPA3 is joined with WPA3, but nothing records that it was.
- No roaming: the station stays with the access point it joined.
- A network whose SSID is not valid text is listed but cannot be added; a hidden network is not listed.
- A lease is not renewed during a stay.
- The router serves one computer, over IPv4 alone, and through the modem alone; nothing outside begins a flow to the computer.
- The tunnel takes one config of one peer that takes every address, and begins every handshake itself.
