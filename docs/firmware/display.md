# Display

How frames reach the panel. What the screens show is described in [Style guide](../app/style-guide.md) and [Interface](../app/interface.md).

## Pages

`fb0` is 32 bits per pixel with three pages (`crates/impshell/src/display/fb.rs`). A frame is drawn into a page not on screen, the one after the page on screen while frames change, and shown with `FBIOPAN_DISPLAY` at the next refresh. The driver's pan returns once the frame that read the page shown before has ended and the drawn page is set for the next frame (`primary_display_trigger` with blocking set waits for the frame's end, after leaving the idle manager's decouple mode), so the page a flip left may be drawn into at once. `r1_funcore::gfx::panel` computes the page layout from what the driver reports (`Geometry`) and tracks which frame each page shows and which page is on screen (`Ring`).

- The framebuffer is never read: its memory is uncached for the CPU.
- `Framebuffer::set_power` blanks and unblanks the panel with `FBIOBLANK`, which also powers the touch panel and the wheel down and up. The panel is blanked as the device sleeps or the screen goes dark during a task, and unblanked as the next frame is drawn (`Light::is_coming_back`): the panel's init blocks the call 0.6 s ([Power](../hardware/power.md#suspend)), which then falls after the pass's tick, so a button let go meanwhile is read before the next tick counts a hold to talk, and a waking press has started the microphone before it. The call is made only when the state changes. After a blank, every page's content counts as unknown.
- The backlight is driven from `display/backlight.rs`. The main loop hands the colour roles of the current theme's palette (`r1_funcore::gfx::palette::Roles`) to the threads that render pages (PDFs) in the interface's look (`App::follow_settings`, `set_roles`).

## Drawing only what changed

`r1_funcore::gfx::pen`. A frame runs through its drawing code twice:

1. The first pass lists every drawing (fill, picture, stretched picture, text, scaled text, stamp, outline, outline over the frame) with the box it may touch and a key of everything that determines its pixels, and compares the list with the previous frame's, entry by entry. Where an entry differs, its old and new boxes count as changed.
2. The second pass draws each drawing only inside the area that changed since the frame its page shows, cut into non-overlapping rectangles. A page that already shows the whole frame is skipped. The changed area is tracked as one bit per group of columns, sized so a row is one machine word (eight columns on the R1); pixels next to a change are redrawn too, in drawing order, so they come out as before.

- **Drawing reads the interface and changes nothing of it.** Both passes run the same code over the interface as it stands (`&Ui`), so they list and draw the same drawings. What a frame reads that is made for it is made before the first pass (`Ui::ready`): the time its fields tick by, the room kept under the bar painted where it changed (`Ui::ready_room`), and the screen under a window that rises or falls, drawn whole into a picture of the screen's size made with the interface (`Ui::ready_beneath`), which the frame copies under the window. While a frame is drawn, only its scratch is written: the texts it writes into (`word`, `bar_text`, `run_time`), the mask a plate's disc is traced in, the canvases below, the robot's list of outline points (`Robot::trace`), and whether a field ticked (`TickerClock::is_seen`) and the bar wrote its word (`BarWord::is_drawn`).
- **A frame that changes nothing** of the frame before, on a page whose content is known, is the frame on screen (`FrameKind::Same` from `DisplayList::frame`): it takes no number, no refresh shows it, and no `FBIOPAN_DISPLAY`, frame record or console line is made for it. Its page is drawn only where it lags behind the frame on screen, and the next page not on screen is drawn into after it (`Ring::skip_back`), so the pages catch up while nothing changes and the next change draws only itself. While something moves, the loop waits for the panel's next refresh after such a frame instead of blocking in the ioctl (`Frames::note_unchanged`, `app::next_motion_ns`, `app::wait_time`), and the run of frames counts the frame as one that came with that refresh, late where it was drawn too slowly for the refresh after the frame before.
- A picture's key contains a number its owner renews whenever the content changes, and only then (`gfx::key::Ids::next`): the viewfinder's picture and a video's are renewed when the camera or the gallery puts a new one in (`Ui::note_finder_frame`, `Ui::note_roll_frame`), not when they are looked into. A plate a frame paints for itself (a recording's mark and time, a viewfinder's word, a bar turned for the way the device is held, the character under the finger large over its key, the chosen thing of a roll turned as it grows) is keyed by everything it shows (`kit::draw_plate`) and painted into a canvas its display list keeps (`Pen::plate`, `Pen::stretch_canvas`): on the second pass only, where some of it is drawn and its key is another than the canvas holds. A bar turned over a video that plays is painted once and copied under every picture after; a recording's mark once a second. Each canvas has its room made with the interface (`DisplayList::reserve_canvas`), the growing thing's as its small picture comes. An outline's key is its points and colours; an outline the previous frame also had is not filled again, its coverage strips are reused.
- A stamp darkens what lies under it, and an outline drawn over the frame (`Pen::cover_over`: the glowing tips of the robot's antennas) blends with what lies under it. For both, the content underneath is drawn into an off-screen picture in cached memory, allocated with the interface so no frame allocates; the stamp or outline is drawn on top and the result copied to the page.
- A page whose content is unknown (after the screen comes back, as a blank forgets every page's frame, or while a host records) is drawn whole.
- **Still frames.** A screen that is left, the screen under a window that rises or falls and a theme's home for its card are drawn whole onto pictures of the screen's size between frames (`Ui::draw_offscreen`), by a display list that keeps no frame before (`DisplayList::offscreen`, `DisplayList::draw_still`): it has one list of coverage strips and no mask or picture in cached memory of its own, and takes those of the frames' list while it draws (`DisplayList::swap_buffers`), as no frame uses them then.

**Pictures in places.** A grid (`ui/grid.rs`) lays out places and chooses among them; it holds no picture. What stands in a place (a line's picture, a small picture of a roll, a theme's card) is kept in `r1_funcore::gfx::store::Store` by the place's spot: the name of its page, which a page laid anew gets afresh, and the thing it holds. The grid tells where a spot is (`Placements`): on the page that shows, in a row that waits or has set off; on a page on its way out; or on none, and then the store lets the picture go as it takes another or steps. A new picture unfolds from the middle of its place over what the place showed once its row has set off; on a page put at rest at once, or on one on its way out, it stands whole. A store that cuts stands every new picture whole at once instead: the roll's grid in type, which shows its pictures without unfolding, and Dial's drum, which keeps the pictures of the things beside its band by thing. A picture made with the same pixels as the one in its place keeps that one's name, so nothing is drawn anew. What a place lets go of (the picture a new one has unfolded over, one cut over, or one a picture of the same pixels replaced) is kept to draw the place's next picture into (`Store::spare`): a place painted anew holds one picture more at rest, and its next picture takes no memory. The roll's small pictures keep none, since the `gallery` thread makes each from the copy it keeps. The icons stamped on a roll's picture show as far as the picture does (`Store::visible_area`).

**Line pictures.** Each line of a list or menu is rendered into a picture when it first shows (`deal_lines` in `ui/view/lines.rs`). The picture is keyed by everything it contains (`Item::to_key`): text, icon, marks, size, every palette role colour; on Deck's chat card the item holds the robot's name and last reply (`Ui::item_of`). A line is painted only where its place holds no picture of that key (`Store::holds`), so one whose picture already matches is not rendered again: a battery step, a swipe home while at home, or going back to a menu renders nothing; a battery step on the settings menu renders only the power line. A list's layout is planned (each line's shape in the current theme) whenever its lines are built from its content; a wheel step onto another page renders that page's pictures with the existing plan (`wheel_lines`), and in Dial, which keeps every line, renders nothing. A field too long for its space is not part of the line's picture: the picture leaves the space empty, and each frame draws the field into it at its current scroll position (`Ticker`, `TickerClock` and `draw_tickers` in `ui/field.rs`). While fields scroll, a frame draws only their spaces; while they rest, nothing. Dial's band keeps the picture of its line in a store of one place (`Dial::take_band` in `ui/list/dial.rs`, `deal_band` in `ui/view/lines.rs`): a line the dial rolls into the band is painted into the picture the band let go of (`Dial::paint_selection`) and stands whole at once, so a line scrolling into the band allocates nothing, and the same line painted anew where it stands unfolds over its picture; a line, a card or a theme's card painted anew in its place is drawn into the picture its place let go of last.

**Kept pictures.** The text screen, the chat screen, the browser, the Pokédex, Signal's conversations and the translator each keep a picture of everything under the bar, 480x543 (about 1 MB), in a store of one place (`RoomPlate` in `ui/textroom/mod.rs`), its memory made ready when the screen opens or the theme changes under the conversation, not by a frame. When the content scrolls by less than the picture's height, the picture is shifted where it stands and only the uncovered rows are drawn; in the conversation, changed rows are drawn from the first changed row down (`Store::repaint`). The picture is drawn whole when the content is laid out again: each screen lays its rows out as it opens, and the conversation's, the Pokédex's result and the browser's page, which outlive a change of theme, are laid out anew then (`Ui::reflow_rooms`); it is drawn whole when the palette changes (`Ui::renew_rooms`). A picture drawn whole while its room shows (another theme or palette, a text that changes while it is read, the Pokédex's next result, the browser's next page, the translator's next session) unfolds from the middle over the picture before, which the store keeps until it has and then gives the next whole picture to be drawn into; one drawn as its screen opens is put to stand whole at once (`Store::put`), and in Terminal every one is cut in. The picture is painted before a frame (`Ui::ready_room`); the frame copies the parts that differ from its page, then draws the scroll mark, the bar and the robot on top.

**Long texts** are laid out one screen ahead at the click and one more screen each frame (`lay_more` in `ui/screen/reader.rs`, `Blocks` in `r1_funcore::domain::paper::markdown`) until complete, so opening a long text costs what opening a short one does.

## Shapes and text

- **Icons** are SVG paths (commands M, L, H, V, Q, T, C, S, Z), read by `r1_funcore::gfx::icon` in the coordinates of the `viewBox` and filled into a mask by the nonzero rule (`r1_funcore::gfx::mask`), each pixel shaded by the share covered, in 256 levels. Curves are flattened to within 1/8192 of the icon box. A file with named paths (`id`) is read path by path. Only paths are read, no other shapes, arcs or opacity. The ignored gate test `material_symbols_match_librsvg` requires every Material Symbols icon and `catching_pokemon`, the one older Material Icon the interface draws, to match librsvg's rendering of its file to within 1/16.
- **Text** is PSF2 (`gfx/font.rs`), drawn one run of lit pixels at a time (`Surface::text`): a glyph row is one word of bits, clipped to the visible part, its runs found by counting zeros. A test compares every glyph of both faces, in every lettering and clip, with bit-by-bit drawing. Bold is one pixel wider; italic shifts one pixel per six rows (`Lettering`).
- **What a run of characters draws as** is read in one place (`gfx/glyph.rs`): an emoji's picture, else Spleen's letter, else GNU Unifont's drawing, else `?`. Every measure of writing counts cells (`glyph::cells_of`), so lines are wrapped and cut by them, and never inside an emoji. The characters Unicode has a reader pass over (its `Default_Ignorable_Code_Point`: the soft hyphen, the joiners and marks of width zero, the variation selectors, the tags), the tones of skin and the keycap take no cell and are drawn as nothing.
- **Unifont** draws every character Spleen lacks and Unifont has, but those of private use and the emoji that show as pictures by themselves: 113,120 drawings, 16 rows tall, 12,169 of them 8 wide and 100,951 16 wide, in `assets/unifont/glyphs.bin`, each kind in the order of its numbers and found by halving (`gfx/unifont.rs`). One 8 wide takes a cell of the font, one 16 wide two, in the colour of the writing. It is grown to the font's height with strokes as strong as Spleen's there (`Drawing::grown`): in the body font, one and a half times its size, an upright stroke is two pixels and a level one is one; in the heading font, twice its size, both are two. No stroke breaks and none joins another. Lettering leaves it as it is. Letters stand apart and in the order they come: a script whose letters join or run from the right, as Arabic's, Hebrew's and Devanagari's, is drawn letter by letter from the left.
- **Emoji** are Noto Emoji's pictures in their own colours, whatever the palette (`gfx/emoji.rs`): 1,967 in `assets/noto/emoji.bin`, each by its sequence of characters, with 15 colours of its own and a picture for each font, 24 and 32 pixels a side, which fills two cells; where the picture leaves the ground, what lies under it stays. An emoji of several characters is one picture: a flag of two letters or of tags, a key cap, and emoji joined by the joiner of width zero; where no picture is of the whole, the longest part that has one is drawn and the rest after it. A tone of skin goes with its emoji and changes nothing. A character Unicode shows as a picture by itself (`Emoji_Presentation`) is one wherever it stands; any other, a heart or a digit, only before the selector that asks for a picture (U+FE0F).
- **A PDF** draws Spleen's characters alone, the quotation marks Spleen lacks (`„`, `‟`, `‚`, `‛`) as `"` and `'`, and keeps a quotation mark's own character for copying. Its rows are measured in the screen's cells, and it draws by them (`glyph::letters`, `Pdf::add_text`): a `?` in each cell of what the screen draws as a drawing of Unifont's or an emoji, two for a wide one or a joined emoji, one for a letter no font has, and nothing for what the screen draws as nothing.
- **Scaling.** A picture that grows, shrinks or is stretched is scaled every frame, each pixel interpolated from four in quarter steps (`Surface::stretch`); a static picture is copied. A picture of pixel words drawn smaller once is the mean of the whole pixels each of its pixels covers, each byte by itself (`Surface::shrink`); a photo's and a call's far picture are shrunk as planes, before they are made words ([Architecture](../architecture.md#media-and-hardware)).

## Timing

- Every moving edge is a damped spring stepped in 1 ms steps (`r1_funcore::gfx::motion`). While frames run back to back, the motion clock advances exactly one refresh per frame (`r1_funcore::gfx::refresh`), so an early or late frame does not jump. Of a gap longer than 100 ms, 100 ms move things and the rest is dropped.
- While a viewfinder's pictures stream the main loop draws only when a new picture has arrived (`r1_funcore::domain::app::frames::Stream`, `should_draw`). The stream's first picture is skipped if it waited through a page flip; after a late picture, once back in step, one picture is skipped to regain the refresh (`gfx::refresh::Catchup`). A video that plays counts as motion (`Ui::is_playing`): a frame is drawn every refresh, with the picture the gallery hands over in the pass's tick (`Gallery::take_frame`, `Ui::note_roll_frame`).
- The main loop watches every run of frames while something moves, and a viewfinder's from its first picture to its last. A run in which a frame arrived closer to two refreshes after the previous one than to one logs `frames: L of a run of N came late, ...` (`of a viewfinder's run` for a viewfinder) with the longest interval and the slowest draw; a clean run logs nothing. At the logging level `debug` the console and the `frames` file get a record per frame ([Console](console.md), [Logs](logs.md#the-logging-switch)).
- **Pacing test** (debug screen, console `anim on` and `anim off`): a frame every refresh, each timed (frame interval, draw, present), with a block moving 240 px per second (`SWEEP_PIXELS_PER_SECOND`), a whole number of pixels per frame, so a late frame shows as a jump. It stops when its screen closes and at sleep, and allocates nothing. `anim off` answers three lines, `frame ms MIN/AVG/MAX n=COUNT`, `draw ms MIN/AVG/MAX` and `present ms MIN/AVG/MAX`, for example `frame ms 16.6/16.6/16.8 n=3`; with no run to tell of, each says `off`.
- While a host records the screen, the recorder's encoding keeps the little cores' clock up, so frame timings taken then do not reflect normal use.

## The drawing thread

The drawing thread is real time ([System](system.md#the-app)), with its core clocked by load: the minimum utilisation a real-time thread otherwise gets is set to zero. Real-time priority is needed because of the kernel's `charger_thread`, which on a USB cable talks to the charger chip in dozens of short steps; with the drawing thread at ordinary priority, it and a kernel worker take the core back after each step and triple a draw. With real-time priority, frame intervals on the cable stay within 15.8 to 17.5 ms and the slowest draw at 6.2 to 6.9 ms.

A resting screen leaves the core at the lowest clock its load needs: at home with the robot, a little core at 400 MHz. At that clock a click that opens a menu takes 11.2 to 13.2 ms (3.6 to 6.1 ms at full clock), and its frame would miss the refresh. So the work a touch, a button or the conversation triggers, and the frame that shows it, run at full clock: the thread asks a floor of the core's whole capacity under its clock (`hw::FULL_LOAD`, `sys::set_clock_floor`, as `r1_funcore::domain::app::Boost` says). The floor is lowered to none (`hw::GOVERNED`) at the first loop iteration without input, and it only applies while the thread runs. Heavy frames also get the full clock (`Ui::is_straining`): a roll's grid growing or shrinking, its carousel or drum moving; a screen transition (except a printed one); the window that scans a code, the key's or the tunnel's, rising or falling; the themes' cards while they are built, one per refresh; the conversation drawn whole. All except the roll's apply only on a lit screen.
