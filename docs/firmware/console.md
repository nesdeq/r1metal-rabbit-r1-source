# Console

A line protocol over the gadget's CDC ACM function. The gadget (`1d6b:0104`, product `r1metal console`) is composite (class `0xef`, subclass 2, protocol 1), as `r1_funcore::hw::usb` describes it, and also carries the USB drive, the screen recording function and the network adapter a computer is lent the modem's connection over ([Network](network.md#router)). Verbs are defined in `r1_funcore::domain::console`. Device side: `usb/console.rs`, `app/console.rs`, `app/shell.rs`. Host side: `link/console.rs` and `remote.rs` in the flasher, which parses every command with the firmware's own parser before sending it.

- Each time `r1` opens the console to read answers, it sends `ping` with a word unique to this session and discards everything before the matching answer, so the rest of an interrupted reply is never taken for the next command's. A firmware that does not accept a word refuses the ping, which also ends the discarding.
- Two commands the main loop answers at once, `key` without an argument before a flash and `record off`, get 2 s (`Console::ask_at_once`, `ANSWERS_WITHIN` in `link/console.rs`), and never one the device answers once another thread has done it (`Command::needs_thread`: `key KEY` and the debug shell's verbs, `tunnel` among them); a console that has not answered by then counts as silent. Every other command is waited for as long as the device takes.
- A batch (`r1 sh -`, one command per line of standard input) prints `$ line` before each reply and `! error` for a refusal. It continues after a refused command and stops at the first link error.

| Direction | Line | Meaning |
|---|---|---|
| host to device | `verb [arguments]` | a command, at most 8192 bytes (`LINE_BYTES`); a longer line is discarded up to its end and answered `err a line without end` in its turn among the lines' answers (`TOO_LONG`, `wire::Line`) |
| device to host | `# text` | a log line, unsolicited |
| device to host | `# frame N t_us=T draw_us=D present_us=P` | a frame, while something moves or a viewfinder shows a new picture, at the logging level `debug` alone ([Logs](logs.md#the-logging-switch)) |
| device to host | `# event E` | an input event: `PttDown`, `PttUp`, `Wheel(n)`, `TouchAt { x, y }`, `TouchUp`. A finger on a keyboard is `TouchAt on a keyboard`, without the position, which would reveal what is typed |
| device to host | `# frames: L of a run of N came late, ...` | the end of a run in which a frame missed its refresh |
| device to host | `# shows: SCREEN [WHICH]` | whenever the visible screen changes: `STAGE` with the icon in the middle, or the screen (`DEBUG`, `VIEWFINDER PHOTO`, `ROLL VIDEO`, `KEYBOARD PASSWORD`, `NOTES`, ...); in Rail, while the wheel turns the rail beside the screen it opened, `HOME`, or `MENU` under home, with the line the rail rests on; not the selected line |
| device to host | `> text` | reply payload |
| device to host | `ok` or `err reason` | end of a reply |

Frame records and events also go to the logs ([Logs](logs.md)). Log lines the host does not read in time are dropped (`r1_funcore::domain::console::outbox::Outbox`). After a command that drops the USB link, nothing is sent until the host has enumerated the device again.

## Verbs

Every firmware accepts these (`r1_funcore::domain::console::command::VERBS`; `r1 sh --help` lists them).

| Verb | Does |
|---|---|
| `ping`, `ping WORD` | answers `> pong`, or `> WORD` |
| `reboot`, `bootloader`, `poweroff` | restarts, restarts into the bootloader, or powers off; `bootloader` is how the flasher reaches fastboot from a running device |
| `input ptt down`, `input ptt up`, `input wheel N`, `input touch X Y`, `input lift` | injects that input into whatever shows |
| `input pose upright\|right-up\|upside-down\|left-up` | a viewfinder or a large video behaves as if the device were held that way, until the accelerometer reports otherwise; refused where nothing rotates |
| `anim on`, `anim off` | the frame pacing test; `off` answers with its statistics ([Display](display.md#timing)) |
| `clock SECONDS MINUTES` | sets the clocks to seconds since the epoch (UTC) and the UTC offset to minutes; `r1 sh clock` sends the host's |
| `time` | queries the time and place services on the timekeeper's thread; the log records the result ([Sleep and clock](sleep.md#clock)) |
| `radio on`, `radio off` | keeps the radio core powered until `off` or the next sleep; a core that does not come on stays off until the next `radio on` |
| `link on`, `link off`, `link cell` | joins the default network, or the modem's connection, and stays until `off`, a sleep or the network is lost; after a failed join or a loss, the next `link on` or `link cell` joins anew; `link cell` passes WiFi over: a WiFi stay that stands ends, and every stay goes over the modem until `on`, `off` or a sleep ([Network](network.md#mobile-data)). `link on` is refused where no network is known and the modem takes no asks (`no network is known`), `link cell` where the modem takes no asks: it is off, its SIM is not ready, or it waits out a failed connection (`the modem is not ready`) |
| `camera on`, `camera off` | runs a video call's camera with no call until `off` or the next sleep, as a call sends this side's picture: the sensor's high speed stream, 640x480 at 30 frames a second, through the front camera, or the rear one where the last video call was turned to it, drawn at the width the call's screen shows it and shown nowhere; no picture is made for a far side ([Camera](camera.md#a-calls-picture)). A viewfinder on the screen takes its place while it shows; taken asleep it holds nothing. For measuring the stream: each run's log line tells its frames and its seconds. A camera that failed stays off until `camera off` |
| `news` | builds the day's edition again, of the rundowns the owner keeps and has made ([News](../app/news.md#schedule)) |
| `chat TEXT` | the conversation takes `TEXT` as if typed on its screen, whatever shows; the reply is spoken unless muted ([Chat](../app/chat.md)) |
| `record on`, `record off` | starts a screen recording, answering with its start time, or stops it; refused without the screen recording function or a screen |
| `key`, `key KEY` | without an argument answers `> kept` or `> none` for the OpenAI key. With a key (which must have a key's shape) stores it in place of any earlier key and answers once it is stored, `ok` or `err not kept: ...`; a line sent after it waits for that answer. `r1 key` sends it with a key it has checked ([OpenAI](../app/openai.md#the-key)) |
| `log off`, `log on`, `log debug` | sets the logging level, as the debug screen's `LOG` line does, and stores it ([Logs](logs.md#the-logging-switch)) |
| `pin PIN` | hands the SIM its PIN, 4 to 8 digits, as `SIM PIN` on the device does ([Interface](../app/interface.md#mobile-data)); when it goes to the SIM and when it is kept: [Modem](../hardware/modem.md#in-r1metal); a log or the console's own lines tell `pin (given)` |
| `attach on`, `attach off` | keeps the modem attached between stays, its radio on and its connection idle, through sleeps too and past the keep it holds after a stay by itself, until `off`, which detaches it at once, or once such a keep that still runs ends; for measuring what an idle attach costs ([Modem](../hardware/modem.md#in-r1metal)) |
| `at COMMAND` | sends an AT command to the modem in its turn; the log tells the answer's lines and how it ended, as `cell: AT+CEREG? answered +CEREG: 1,1 \| OK`, the command's arguments left out, as they may hold a PIN; with the modem not ready, the log tells that instead. A command that changes how the modem reports, as `AT+CEREG=4`, changes what the firmware reads |

## Debug shell

These verbs (`r1_funcore::domain::console::command::SHELL_VERBS`) exist only with the `debug-shell` feature of `r1-impshell`. The feature is on by default, so every `r1 build` has it; it also mounts the tracer at `/sys/kernel/tracing`. The verbs run one after another on their own thread, `shell`; the main loop only forwards finished answers, and a line sent after one waits for its answer (`r1_funcore::domain::console::queue::Queue`). `r1 pull`, `push` and `logs` use `ls`, `read`, `append` and `rm`; `r1 pull` lists what it is given and reads it as a file if it is not a directory. `r1 backup` and `restore` use `ls`, `read`, `mkdir`, `append` and the verbs of [the gate](#the-gate). `ls` leaves Signal's directory, the tunnel's config, the safe's key files, a restore's files, every `mem` file, the modem's record and every file held in memory alone out of a listing, and every verb on files, reading or writing, refuses a path to them, however written: the shell asks once, before it runs a verb, of the path the verb reads or writes (`Command::path`, which every verb answers), and funcore decides on the path as the file really is (`console::shell::is_denied`): Signal's files ([Signal](../app/signal.md#files)), the tunnel's config (`/data/.r1metal/router`, which holds its private key, [Network](network.md#router)), the safe's key files, written or half written (`/data/.r1metal.key`, `/data/.r1metal.key2`, `safe::KEY_FILES`: each holds the safe's key sealed under the passphrase, which whoever reads it may try passphrases on, [Storage](storage.md#the-safe)), and a restore's, staged or confirmed (`/data/.restore.new`, `/data/.restore`), all reached once the gate is open; the `mem` file of every process and thread, as `/proc/N/mem` and `/proc/N/task/T/mem` (the app's holds Signal's keys once the safe is open, and the kernel shows each of its threads as a process of its own too); `/dev/mem`, physical memory, which the kernel is built without ([Kernel](../hardware/kernel.md)); the kernel's record of the modem's ports, `/proc/ccci_dump`, which holds every write to `ttyC0`, a PIN's among them ([Modem](../hardware/modem.md#measured-on-the-r1)); and every file held in memory alone, whose link in `/proc/N/fd` reads `/memfd:` and its name: what is said to a voiced job, the conversation, the browser, the bell, the rundowns' list, the Pokédex or a Signal draft, is recorded into one (`sound::Memo`). A path is taken as the file it names really is: through links whose end cannot be followed (a file deleted while it is open, as `/proc/N/fd` shows one, or a link to what is not there yet) as each reads, from the directory it really lies in, until one is no link or one comes again; and where its last parts are not there yet, as they are written (`console::shell::to_real_path`). A path that climbs with `..` among parts not there yet is refused, as where it leads is decided only as they are made, so that `mkdir` makes no way in either.

| Verb | Does |
|---|---|
| `ls PATH`, `cat PATH`, `dmesg` | a directory's entries; a file's text, and of what has no end, a device or a pipe, what it has at hand, its first 49152 bytes at the most (`shell::most_read`), read without blocking, as `read` and `sum` read too; the kernel log |
| `write PATH TEXT`, `rm PATH`, `mkdir PATH`, `rmdir PATH` | writes a file; removes one file; creates a directory with its parents; removes an empty directory |
| `read PATH OFFSET LENGTH`, `append PATH BASE64` | part of a file as one base64 line, at most 49152 bytes (`command::READ_MOST`, what `r1` asks for at a time; a longer one is answered `err a read takes at most 49152 bytes`); appends decoded base64 to a file (no directories created). A `read` of `/dev/fb0` must start at a multiple of 8 bytes; an offset 4 bytes off reads zeros where the screen is lit |
| `sum PATH` | the SHA-256 of a file's bytes, in hexadecimal; of a device or a pipe, of what it has at hand, its first 49152 bytes at the most |
| `unlock PASSPHRASE`, `lock` | opens the gate where the passphrase is the safe's, and shuts it; a log or the console's own lines tell `unlock (given)` |
| `stage`, `commit` | makes the directory a restore's files are staged in, in place of what was staged or confirmed before; confirms the staged files, which take the partition's place at the next start. Both only with the gate open ([Storage](storage.md#backup-and-restore)) |
| `bench` | times by the monotonic clock (`domain::console::bench`), on the shell's thread: two seconds of a call's pictures at 640x480, made up as a camera's are, coded by the VP8 encoder at a fixed quantizer, first with a sensor's noise in every sample, modelled and not measured, and then clean, the clean frames decoded; a group call's VP9 stream (`vp9::SVC`) decoded in whole passes to as many frames at least; the camera's pictures of its raw frames, each made 60 times on one thread as the camera makes it: a call's picture of a high speed frame, the photo viewfinder's of a preview frame and a recording's planes of a slim video frame; the far side's picture of a call made 60 times of the clean scene's first picture, coded as a key frame and decoded, in each of the far picture's two rooms, upright and turned a quarter; and each kernel of `base::simd` in `bench::KERNELS` ([Architecture](../architecture.md#media-and-hardware)) by its plain body and its NEON body over the clean pictures. Then, for each scene, clean then noisy, on a thread of its own kept on the first large core (`Crew::on_cores`), the pictures coded as a call codes them, each step's work on it and a crew of the other three large cores, once untimed, so that the crew's threads stand started and waiting as a call's do before its first picture, then with each of the six steps timed; then, for each of the camera's pictures, on another thread of its own kept on the first little core, the picture made in as many parts as the camera makes it in on it and a crew of the other seven cores; last, on a thread of its own kept on the first large core, that thread and the first thread of a crew of the other three large cores taking turns, each parked until the other has taken its turn and wakes it, `bench::WAKES` turns each, as many as a coding's pictures, as a wave's row that waited is woken. Answers a line for each: for each scene `encode 640x480: 60 frames of B bytes, T us each, on core C at F MHz` and `encode 640x480 on the large cores' crew: 60 frames of B bytes, T us each (interpolations I us, bands B us, code C us, counts N us, probabilities P us, ends E us), the longest L us, on core C at F MHz`, the noisy scene's named `640x480 with modelled sensor noise`; `a parked thread woken: T us, on core C at F MHz`, T the turns' whole time over the turns of both threads, a turn's park and wake on the mean; `decode VP8 640x480: 60 frames, T us each, ...`; `decode VP9 320x176 in three layers: 60 frames, T us each, ...`; `call picture 640x480 of a raw frame: 60 pictures, T us each on one thread on core C at F MHz, T us each in 8 parts on a crew of every core on core C at F MHz`, and as it `photo viewfinder 480x480 of a preview frame` in 4 parts and `recording 1280x720 of a slim video frame` in 8; `far picture 640x480 in a room of 301x535 upright: 60 pictures of WxH, T us each, on core C at F MHz`, and as it in a room of `301x535 turned a quarter`, `464x321 upright` and `464x321 turned a quarter`; and for a kernel `sad 16x16: plain P us, NEON N us a picture, S.SS times`. A case's core and its cluster's clock are as the kernel tells them at the case's end (`sched_getcpu`; `scaling_cur_freq` of `cpufreq/policy0` and `policy4`, each named for its cluster's first core, `sys::CLOCKS`), `on core C` where the clock is not read, `on a core not told` where the core is not. Where another target builds no NEON body, both times are the plain body's |
| `tunnel BASE64` | hands over a tunnel's config, the text `wg-quick` takes, in base64, which the router's thread keeps in place of any before it; answered once it is kept, `ok` or `err not kept: ...`, or at once with why it is no config the router takes ([Network](network.md#the-tunnel)). Only with the gate open, as its file is behind it; the main loop reads it where the gate is and hands it to the router's thread, and a log or the console's own lines tell `tunnel (given)` |

### The gate

The shell keeps Signal's files, the tunnel's config, the safe's key files and a restore's from every host that has not given the safe's passphrase (`console::shell::Gate`, on the shell's board):

- `unlock PASSPHRASE` has the storage check the passphrase as it checks the one in use before a change: it opens the safe's key in a key file with it, or does not, and adds no key to the filesystem (`Data::check_passphrase`, `safe::check`). The safe's own opens the gate: `ls`, `read`, `sum`, `append` and the other verbs on files then reach Signal's directory, the tunnel's config, the key files and `/data/.restore.new`, and `stage`, `commit` and `tunnel` run (`shell::State::check`, which answers a denied path before a verb the shut gate keeps, and `shell::State::read_tunnel`). Nothing else opens: the `mem` files, the modem's record and the files held in memory stay denied.
- A wrong passphrase answers `err a wrong passphrase` and is logged as one. After three wrong ones in a run of the app (`safe::ATTEMPTS`, the count that powers the device off at the safe's window), no passphrase is checked any more until the R1 starts anew. With the safe not open, or with no key file that reads, none can be checked (`err the passphrase could not be checked: the safe is not open, or no key file reads`).
- `lock` shuts the gate, and so does the port's hang-up, as a cable pulled or a host that leaves makes one: a passphrase still being checked then opens nothing.
- The passphrase comes as a line of the console, as a key and a PIN do, and is a `safe::Passphrase` from its parse on.

## Screen recording

`r1 record FILE.mp4` records the screen into an H.264 MP4 at the panel's 60 frames per second until Ctrl-C; the host's `ffmpeg` encodes it. Nothing on the device starts or shows a recording. Code: `usb/frames.rs`, `display/recorder.rs` and the render path in `app/frame.rs`; `r1_funcore::domain::recording`; `link/frames.rs` and `record/` in the flasher.

- **USB function.** FunctionFS `ffs.frames` at `/dev/usb-ffs/frames`: one vendor interface (class `0xff`, subclass `0x52`, protocol 1, `r1metal frames`) with one bulk IN endpoint, 512-byte packets at high speed. Process 1 sets it up before the app binds the gadget and keeps `ep0` open for good, because closing it removes the whole gadget from the bus. The app inherits the file, reads the kernel's events from it and stalls every request a host makes of the function. If the controller refuses the gadget with this function, the gadget is bound without it.
- **Drawing.** While recording, each frame is drawn into one of three buffers in cached memory, copied to the screen's page and shown; the framebuffer is still never read. The newest frame replaces any frame still waiting for the sender (which counts as skipped), so the newest frame is never lost to a slow link. A dark screen is recorded as one black frame.
- **Sending.** The `recording` thread compares each frame with the last one sent in 16x16 blocks and sends the changed blocks; the first frame goes whole. A block is 4:2:0 YUV in BT.709 limited range: 256 luma samples, then 64 Cb and 64 Cr samples, each the mean of 2x2 pixels. The thread processes 16 lines at a time and converts a band's blocks while the band is in cache. A record goes to the kernel in 32 KiB parts (eight pages: the largest allocation the kernel does not treat as costly, and under the controller's 16-bit request limit) through asynchronous I/O, up to one whole frame's parts at once (15, `recording::depth`). FunctionFS copies each part as it is submitted, and the controller sends queued parts back to back. A failed part ends the recording, and so does a host that takes no part for 5 s (`recording::HOST_TIMEOUT`), which counts as gone; a lagging host gets frames skipped meanwhile. An ended recording waits until everything is sent, or until the host has taken nothing for as long.
- **Records.** A 24-byte header (`R1RC`, type, the monotonic time in microseconds from which it shows, body length, frames skipped since the previous record) and a body. A start record carries the screen's size and rate, a frame record its size, block count and each block's position and samples, an end record nothing more. A header with an unknown type, or a length no record of its type has, is a chance match inside other bytes and is skipped, so the host never stalls on one.
- **Host side.** `r1` sends `record on` and releases the console, so a script can drive the device meanwhile; it opens the console again only for `record off`. A device that does not get `record off` in time ends its recording once nothing reads its frames. The host keeps two transfers pending on its own thread and starts from the start record whose time `record on` returned, skipping anything an earlier recording left in the pipe. Each frame is placed at the nearest point of the video's frame grid and repeated until the next frame's point; the end record's time ends the video, and the last frame shows at least once. Pictures go to `ffmpeg` as raw I420, encoded by `libx264` with its defaults, tagged BT.709 limited range. The first Ctrl-C sends `record off` and waits for the last frames; a second one exits at once. `r1` prints the video's length, frames received, frames skipped and bytes; the device logs `recording: ended, F frames sent and P passed over, B bytes in S s`.

A frame that changes every block is 1200 blocks of 386 bytes, 463 KB with its header; 60 per second is 27.8 MB/s. Encoding a frame that changes every block takes 3.3 ms on a big core at 2.2 GHz and 4.1 ms on a little core at 1.6 GHz; a frame of stage motion takes 2.3 to 2.8 ms to draw and copy while recording.
