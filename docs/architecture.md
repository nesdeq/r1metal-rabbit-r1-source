# Architecture

How r1metal is built: the law between the kernel, impshell and funcore, the rules every change follows, the one home of each concept, and the rule a new piece of code of that kind follows. Read this page in full before changing the code.

## The law

Linux 4.19 is the driver layer; one static binary is `/init` and the entire userspace, with no shell, no libc on disk and no init system. The firmware follows the functional core and imperative shell pattern (Gary Bernhardt, "Boundaries", 2012):

- **funcore** makes every decision. It takes values and returns values, returns the same output for the same input, and is tested on the host.
- **impshell** performs the effects. It reads the world into values for funcore and carries out funcore's results, with as few code paths as possible.
- Code goes into the kernel only where userspace cannot do the job, into impshell only where it makes an OS call or uses a library, and into funcore otherwise.

| Layer | Location | Contains | Never contains | Enforced by |
|---|---|---|---|---|
| Kernel | Rabbit's 4.19 plus `kernel/` ([Kernel](hardware/kernel.md)) | drivers and what only the kernel can do: interrupt handlers, DMA and the IOMMU, power domains and clocks, suspend and resume; the device tree; the configuration | anything userspace can reach through a device node, a mapping, a sysfs file or a socket | patches in `kernel/patches` and `kernel/module-patches`; the stock configuration `kernel/config` and r1metal's changes `kernel/config.changes` |
| impshell | `crates/impshell`, the `/init` binary | system calls, file descriptors, mappings, threads, waits, clock reads; the layout of call arguments (`ioctl` numbers and structs, `sockaddr`, `mmap` offsets); paths under `/dev`, `/sys` and `/proc`; AWS-LC behind funcore's crypto traits; the libraries called directly: AWS-LC for the safe's key, SHA-1, SHA-256 sums and random bytes, rustls and webpki-roots for TLS, flate2 for gzip and zlib | a decision based on a value: a data format, a protocol, a state machine, on-screen text | `crates/impshell/tests/boundaries.rs` |
| funcore | `crates/funcore`: `no_std` and `alloc`, no dependencies | every decision and data format: the UI and its text, protocols, file formats, register sequences, and data Linux hands over (`/proc` text, kmsg records, nl80211 messages, evdev records) | a system call, a file descriptor, a thread, a clock read, a library, a wait other than `Hardware::pause` and a wave's `crew::Rows::wait` | the compiler, by `#![no_std]` and `deny(unsafe_code)` outside tests, which only `base::simd` lifts; `crates/impshell/tests/boundaries.rs` |

`crates/impshell/tests/boundaries.rs` parses every crate's source, through the one reader of Rust the workspace's checks share (`crates/flasher/src/visibility/syntax.rs`, which the test takes in by its path and `r1 visibility` reads through too), and asserts that:

- the kernel's tracked files are only patches and configuration;
- funcore has no dependencies, builds without `std` outside its tests, and denies `unsafe` there, so it reaches the hardware only through its traits; the one module that lifts the denial is `base::simd`, and no `unsafe` stands outside it;
- funcore keeps no state of its own: no `thread_local!`, no `static mut`, no static of an atomic or interior-mutable type;
- the image crate's readers depend only on their codecs and make no OS calls;
- impshell contains no on-screen text, and outside its tests names none of funcore's words of the screen, by any path, any name a `use` gives it (in a function too), or a glob: it tells funcore why, and funcore picks the word;
- every impshell function touches the world or is plumbing at a call, and a function that branches touches more than a lock, an atomic or a path (a branch next to only those is a decision and belongs in funcore); a method of a handle that branches touches the world the handle holds, as a branch next to only its plain fields is a decision too;
- every impshell test touches more of the world than a lock, an atomic or a path, uses AWS-LC, rustls, webpki-roots or flate2, or checks a kernel layout, number or path;
- every module of funcore's root and of impshell's stands in a layer of the orders below, and no path from its crate's root, by `crate::` or by `super::` up to it, leads from it into another module of its own layer or of a higher one;
- each rule catches what it targets and passes what it does not.

Definitions the test uses:

- **The world**: anything reached by a call outside the language: the OS, a clock read, the thread's error number, whether another thread holds a lock, filesystem state at a path, device-mapped memory, a thread-local static, a handle read, written (`Read`, `Write`) or dropped. A stored time or handle number is a value.
- **Plumbing at a call**: a trait method the language, funcore or a library requires; a method of a handle (a type that holds more of the world than a lock, an atomic or a path) that decides nothing or touches the world the handle holds: a field of its own that holds more of the world than a lock, an atomic or a path, by the fields that lead to it, the handle itself taken apart (`match self`), or a call of what does; a method that passes its parameters unchanged to funcore through a field of its own; a method that takes or returns a kernel structure; a method that calls a library; a method that decides nothing and only builds a call's error or a log line. Unit conversion, field selection and distinguishing a call's errors stay next to the call.
- Names are resolved as their file defines or imports them: an alias is its target type, a path is read past its generic arguments, a module imported with `self` is not a bare name, a call by the name of a function the file defines is of that function whatever a `use` takes by that name, and a name bound by a parameter or a `let` is that value.

Interfaces between impshell and funcore:

The split keeps every decision deterministic and tested on the host, ensures the drawing thread waits only on what it starts itself, and lets a kernel of our own replace Linux with only impshell rewritten.

| Crate | Target | Role |
|---|---|---|
| `r1-funcore` | `no_std` + `alloc` | the functional core: drawing, the UI, protocols, file formats, register sequences |
| `r1-impshell` | `aarch64-unknown-linux-musl` | the imperative shell: `/init`, process 1 and the app, one thread per hardware part ([System](firmware/system.md)) |
| `r1-image` | host; its readers also run on the device | writes boot image v2 and legacy LZ4 (feature `boot`, used by the flasher), newc cpio, vbmeta and device trees; reads Rabbit's `super.img` (sparse image, super partition table, ext4) and cuts it into sparse images of one download each; on the device its ext4 reader reads the factory NVRAM files |
| `r1-flasher` | host | the `r1` tool: build, flash, Rabbit's firmware put back, the OpenAI key; the console, logs, files, screen, backup and restore of a running R1 |

funcore's modules stand in layers, each importing only lower ones: `base`; `crypto`, `gfx`, `codec`; `hw`, `input`, `fs`, `net`; `storage`; `logs`, `cell`, `openai`, `signal`; `wifi`; `domain`; `ui`.

impshell's modules stand in layers the same way: `sys`; `sync`; `pool`, `crew`; `clock`; `crypto`; `storage`; `usb`; `display`, `input`, `media`, `power`; `sound`; `cell`; `wifi`; `net`; `openai`, `timekeeper`; `backlog`, `voiced`; the features (`about`, `aloud`, `bell`, `calls`, `camera`, `chat`, `cost`, `gallery`, `magic`, `memos`, `news`, `pokedex`, `router`, `rundown`, `signal`, `translator`, `web`), none of which imports another; `app`; `pid1`.

## Rules for every change

Every change to funcore and impshell follows these rules; a change that breaks one is a bug, whatever the tests say. Before writing code, find the concept's home under [One home for each concept](#one-home-for-each-concept) and extend it.

### Core and shell

- **F1, a pure core.** funcore does no I/O and holds no threads, waits, clocks, randomness or state it is not handed. It takes values and returns values. It reaches the machine only through its own traits, which impshell implements as relays: each method one effect, no decision.
- **F2, every decision in the core.** impshell branches only on: the outcome of an effect it just made (success, failure, error kind, readiness, end of data); a value funcore returned to tell it what to do; whether there is data to move, and moving each piece of it. Any other branch, comparison, count, threshold, choice of timeout or retry, choice between actions, parse, format or word is a decision: it lives in funcore, and impshell calls it. Where impshell's next step depends on anything but an effect's outcome, funcore returns that step as an enum; impshell matches on it, one effect per arm, and hands the outcome back. A shell loop that picks its next step from several funcore values breaks this rule.
- **F3, every format in the core.** Files, wire messages, model input, and log lines that report funcore's values are made by funcore and written by impshell unchanged. impshell's own text is only a log line or an error that names an effect it made and that effect's error.
- **F4, one shared state.** A shell thread and the main loop share exactly one funcore state value, which holds the report: the shell's inputs as plain fields, the `Report` taken whole, the state machine's own fields private. The means to wake each other (a readiness descriptor, a condition) carry no data. Nothing else passes between them: no extra atomics, locks, flags, channels or queues.
- **F5, parts talk through the main loop.** A part holds no handle of another part and shares no mutable object with one. What one part produces for another leaves in its report; the main loop hands it as a typed value to the other part's input. Only a service may be handed to the parts that use it: a part others need to do their own work, with no user-facing job of its own (a device driver, `storage::Data`, the `Account`, the radio's `Online`, the modem's `Cellular`). A service holds no handle of a part that is not a service.

### Separation of concerns

- **S1.** One module, one concern, named for it. Everything in a module serves that concern; everything serving that concern is in it.
- **S2.** An item lives in the lowest layer that owns its concept, and a layer imports only lower layers, in the orders above. No copy, wrapper, alias or re-export of an item lives anywhere else.
- **S3.** One concept, one implementation. Two types, functions, painters, parsers or code paths doing one job are merged into one; none survives beside the other.
- **S4.** A word only the screen shows lives in the ui. A word that also reaches a log, a file, the network or a model belongs to the layer that owns its concept, and the ui shows it from there. The ui builds no text for a log, a file, the network or a model. The domain returns data and enums, never screen words.
- **S5.** A domain module owns its state, decisions, file format and model prompts. It does no I/O and no drawing.
- **S6.** The ui keeps four concerns apart. Elements draw: each kind of element has one drawing implementation and knows no screen and no theme. Layouts place and style: positions and style values, no drawing. Screens map state to elements and input to actions: no drawing, no branching on the theme or the layout. Composition (`ui/view/`) picks elements, places and calls them, and draws nothing of its own beyond clearing the ground.

### Names, comments and tests

- **N1.** Every module, type, trait, function, field, variant, constant, variable and parameter is named for what it is or does where it stands, in short plain technical words: no participle or phrase standing in for a thing, no invented compounds. A term a standard, a protocol or the kernel defines stays as it is written there (`dpb`, `nl80211`, `ioctl`). The module path carries the context, so a name does not repeat it. A rename changes no output: every literal, path, file name, format key and `Debug` text that reaches the screen, a file, the wire or a model stays.
- **N2.** No comment by default. A comment says in one line, in the present tense, only the why the code cannot show. Doc comments stand on items declared `pub` alone, one line each, saying what the item is for; one that restates the name or the signature is deleted. Every comment and assertion message is true of the code as it stands.
- **N3.** A test is named for the behavior it checks, in a few technical words, never a sentence (`listing_round_trip`), and an assertion's message says what its case shows. Existing tests keep passing; a test moves with the code it tests.

### Exceptions and collisions

- A rule gives way only where keeping it would change what the device does: a sequence tuned on the device (an order of calls or register writes, a timing, a retry measured on the hardware), or a real-time limit the code proves (a callback that must never block). The exception carries a one-line comment with its evidence, and its decision still lives in funcore. That it works, is simpler, or that the shell needs it is no evidence.
- When two rules seem to pull apart, the change satisfies both: split the data from its words, split the decision from the effect, route through the report and the main loop, move the item to the lowest layer that owns it, or give two readers one source in the layer that owns it. Keeping the code as it is, reclassifying a part, a word or a module to exempt it, and a wrapper, alias or re-export that keeps an old path alive are never the fix. What the device does, shows, logs, writes and sends outranks every rule; where no change satisfies both, F wins over S and S over N.
- funcore's one `unsafe` is SIMD's: the call from a kernel of `base::simd`, a safe function, into its NEON body, a function of the `neon` target feature, which plain code reaches only in `unsafe`. Its plain body stays: other targets build it, the tests hold the NEON body to it bit for bit on random and edge inputs, and the debug shell's `bench` times both on the device ([Console](firmware/console.md#debug-shell)); a kernel stays where the device's time shows its NEON body faster.
- `scripts/gates.sh` and `crates/impshell/tests/boundaries.rs` check part of these rules. They are a floor: a change that passes them and breaks a rule is still a bug.

## One home for each concept

Every concept below has one implementation. A new piece of code of that kind follows its rule, and never builds a second copy beside the first.

### Parts and the main loop

- **Starting.** A part whose start needs only eventfds, timerfds, threads and epoll registrations is a plain field of `Parts`, started by `require(…)`, which the bell's alarm in `App` is started by too, watched by `Epoll::add_wakeup` where the parts are watched by `Epoll::add`; a failure ends the app's start and process 1 starts it again. A part whose start needs more is an `Option`: the monitor, framebuffer, recorder, console and tilt. The drive, camera, gallery and shell are `Option`s too, though their starts need only threads and eventfds; the camera, gallery and recorder start only with a framebuffer. The console lives in `Host`, the shell in its `Dispatch`, the tilt in `App`, the rest in `Parts`. The monitor, camera, gallery, console, tilt and shell are started and watched by `watch(…)`; the framebuffer, recorder and drive are started with `.ok()`. The inputs are a plain field opened by `Inputs::open`, which keeps the devices that open. What a part needs of another (`data`, `online`, `account`, `networks`) is bound once in `start.rs` and handed over as a value; the keeper of the clocks and the modem start before the radio, which is handed what every hold has it do (`Timing::hold_hook`) and the modem's side for it (`Modem::cellular`), and the keeper is handed the main loop's `online` with each asking; where it uses one side of another part, it is handed that side alone (`Keeper::settler` for the battery meter, `Keeper::uses` for Signal's unlink, the cost screen's read of the ledger, the about screen's two reads), and the main loop keeps the whole. Only the settings' keeper changes the known networks (`Keeper::change`, the change and the place a join proved in one order). The bell is the interface's: the keeper hands it what an earlier run kept with the settings (`Ui::recall_bell`) and keeps it as it changes (`Ui::take_changed_bell`, `Keeper::keep_bell`). So are the rundowns the owner keeps (`Ui::recall_rundowns`, `Ui::take_changed_rundowns`, `Keeper::keep_rundowns`), which the main loop hands the editor at the start and at each change (`Editor::set_topics`). No funcore type has a mode for a missing part; the debug screen shows `ABSENT` for a fact one leaves empty.
- **Naming.** The parts are named once, in `sources! { … }` (`app/mod.rs`). funcore's `app::to_token` and `app::parse_token` are the epoll token format; `app::is_quiet(&[…])` takes its list at the call, and `app::Debts` what the parts that go on asleep owe the radio, read once a pass.
- **The board.** A part's thread and the main loop share one `sync::Board` of funcore state: the camera, gallery, pixel cam, notes, scribe, translator, editor, reader, keys, Signal, the voiced jobs, radio, keeper of the clocks, rundown, battery meter, storage, settings' keeper and the logs. The modem's thread shares one too, and so do the router's forwarder, on which the threads beside it leave what they found for it (`router::Answer`), and the calls' threads (`calls::state::Answer`). On it the shell's inputs are plain fields, the state machine's own fields are private, and the `Report` is taken whole with `mem::take`. The cost, the about screen and the suspend gate answer a request through a `sync::Fetcher`. The logs keep a lock and flags of their own beside their board, and a drawing thread never waits on the logs. The main loop tells a part what the interface wants through its `want`, the gallery also through `set_home`, the editor through `set_schedule` and `set_topics`, Signal through `want_media` and the modem through `keep_pin`, `hold_attach` and `set_awake`; the state decides whether that is new, and only then are the threads woken. The keys take orders instead (`begin`, `check`, `keep`, `recheck`). What the screens asked goes through `ask`, the gallery's through `add_errand`. The loop takes the part's news through `latest` when its flag is up, which swaps the camera's, the gallery's and the calls' newest picture into the screen's too, and asks `is_off()` before a suspend where the part can keep the device from suspending (`Parts::is_quiet`). The radio is told in seven calls a pass (`set_resting`, `want`, `want_link`, `want_cell`, `want_route`, `want_scan`, `want_trial`); `set_resting` gives what a part that goes on asleep takes for its leave where the rest is lifted (`radio::RadioGrant`), so a leave comes only behind it, and only to the parts `app::Debts::to_grantees` names.
- **Requests between features** are typed enums the main loop routes: `ui::Action` from an event, from `Ui::tick`, from `Ui::ring` or from `Ui::set_call`, carried out in one place (`App::act`), `domain::chat::tools::Act` from the conversation, `Input` for the two together, `Requests` from the console.
- **Latches.** A part told something once until it answers keeps a funcore `handoff::Ticket` or `Latch` in its handle. The `App` keeps one `handoff::Attempt` for a part, the accelerometer's `tilt_attempt`, which tries a missing accelerometer once each time it is wanted: it matters only while the handle `tilt` is none. Its latches keep what the loop last gave the speaker (`levels`), the settings it last handed the parts that follow them (`settings`: the account's terms, the conversation's tools, Signal's said messages, the Pokédex's language, whether the USB drive is shown, `Account::set_terms`, `Chat::set_settings`, `Drafts::set_voice`, `Pokedex::set_language`, `Drive::set_shown`), the palette's colour roles it last handed the parts that draw in them (`roles`: `Editor::set_roles`, `Scribe::set_roles`, `Pokedex::set_roles`), the kernel's log switches (`logging`), the log (`scene_words`, `is_pacing`), the time the bell's alarm is set to and whether the ring's sound plays (`bell_at`, `is_ringing`), whether the searching sound plays (`is_searching`), and how many notices the interface had given (`notices`).
- **Relays.** A part that must hear of another's news through the interface is told through its request: by a counter the Ui raises (`Ui::file_changes`, `Ui::pixel_changes`), or, for the reader, by `Ui::reading_request`, which takes the number of the conversation's reply. The loop relays news between parts in its branches too: the flash's key, which the settings' keeper reads, and a key a service refused go to the keys, and the keys' word that the flash's key is kept goes back to the settings' keeper, which keeps that flash's stamp only then; the reader's word on a reply goes to the conversation, and the conversation's reply as far as it is written goes to the reader (`Reader::set_reply`); the camera's and the gallery's orders go to the pixel cam (`Magic::take_orders`), the photos it redrew to the gallery (`Gallery::add_redraws`), and the photos a roll's stamp asks to redraw from the gallery's report to the darkroom, which makes their copies (`Camera::copy`); a photo the camera took for the robot goes to the Ui (`Ui::take_shot`), which opens the conversation and hands it on among its bids (`Chore::Show`); the item of a roll to send goes through the gallery's report (`gallery::Sending`) to the Ui (`Ui::send_item`), which opens Signal's list for it; the changes a request said to the bell asks go from its job's report to the Ui, which makes each as it makes the robot's (`Ui::take_bell_report`, `Ui::change_bell`), and the bell as it stands goes to the job with each request among the screen's bids (`bell::state::Standing`); what a request for the rundowns comes to goes from its job's report to the Ui, which keeps each rundown and shows a deletion for the owner's click (`Ui::take_rundowns_report`), the rundowns as they stand with the feeds that gave no story go to the job with each request among the screen's bids (`news::request::Standing`), and those feeds go from the editor's report to the Ui (`Ui::take_editor_report`); the robot's questions about Signal go from the conversation's report through the Ui (`Reading::Ask`) to Signal (`Signal::ask_question`), and Signal's reply from its report to the conversation (`Chat::answer_readout`); what Signal's thread has for the call layer, the call messages that passed its gate, the relays, a group's token and the signals not sent, goes from its board to the calls' thread (`Signal::take_call_report`, `Calls::take_news`), the call log and whom a call may go to with it to the Ui (`Ui::take_call_log`), what the call layer asks of Signal goes back from the calls' report (`Signal::ask`), the owner's orders go from the Ui to the calls (`Ui::take_call_orders`, `Calls::ask`) and how the call stands back (`Ui::set_call`), and whether the calls hold Signal's socket is the Ui's word on what shows and the part's on whether a call stands (`Ui::are_calls_wanted`, `Signal::set_calling`); a video call's pictures go the same way: the camera makes a picture for the far side of each frame whose turn comes while the calls' part wants them (`Calls::wants_picture`, `Camera::want_call_pictures`), and the one it made goes to the calls by a swap through a picture of the `App`'s own (`Camera::take_call_picture`, `Calls::add_picture`), the room the far side's picture is fitted to goes from the Ui to the calls (`Ui::far_picture_room`, `Calls::want`), the far side's newest picture is swapped into the Ui's as the calls' report is taken (`Calls::latest`, `Ui::far_picture_mut`), and the camera's stream for the call is the Ui's viewfinder, which the console's `camera on` holds with no call too (`Ui::set_console_camera`), and whose picture the camera swaps into the call's own picture as into a viewfinder (`Ui::call_camera`, `Ui::camera_picture_mut`); the notes' recording and new entries and the translator's new ones go to the scribe (`Scribe::set_recording`, `Scribe::add_new`); a PIN typed on `SIM PIN` goes to the modem (`Ui::take_pin`, `Modem::enter_pin`), as one the console gave does, and so do the console's AT commands (`Modem::send`); a tunnel's config the `TUNNEL` window read off a code, or its word to forget the one kept, goes to the router (`Ui::take_router_order`, `Router::ask`), as a config the console handed over does, whether a computer's link has the router route goes to the radio (`Router::is_routing`, `Radio::want_route`), and what keeping a config came to goes from the router's report to the Ui (`Ui::take_router_report`) or to the console that handed it over (`Host::answer_keep`, which answers for a key the same way); device events go to storage, the drive and the meter; the radio's word that a stay ended goes to the account, which drops the connections the stay left in its pool; a pose, the accelerometer's or one the console named, goes to the camera and the gallery beside the Ui (`turn`). What a part asked another for comes back through the handle it asked by. The screens hear what the notes' keeper, the scribe and the editor are at through `Ui::update_memo_work`, which the loop calls every pass, as what it tells follows the kind that shows as well as their news.
- **Frames owed.** Every `Ui` setter the loop calls says whether what shows changed, and is `#[must_use]`: the loop gives what it says to `Cycle::note_change`, and a call that drops it does not pass the gates. A frame owed wrongly costs a pass that lists what it would draw, since a frame that changes nothing is not shown.
- **Clocks.** Timers inside a session run on the paced clock (boot time); the wall clock is for stamps and kept schedules. A wake alarm is a `power::alarm::Alarm` for a use in `Reason`, set and cleared through `Alarm::arm` alone ([Sleep and clock](firmware/sleep.md#the-alarms-list)).
- **Sleep.** The Ui owns it (`ui/screen/sleep.rs`). `Ui::fall_asleep` makes the `Doze`; asleep, `Ui::handle` gives it the button and `Ui::set_reading` the battery; `Ui::note_wake` ends it. impshell borrows `Ui::doze_mut()` for the kernel's steps, which `Doze::next_step` gives, and switches the screen with the one `App::set_screen(is_on)`; the panel comes on as the next frame is drawn (`Light::is_coming_back`).
- **A new part** costs a name in `sources!`, a `Parts` field, one line each in `start.rs`, `serve.rs` and `steer.rs`, and its `is_off()` in `Parts::is_quiet` where it can keep the device from suspending. Its funcore state has one `want`, an `ask` for its edges, one `Report` and `is_off`; its handle forwards to them and wakes the threads only where the state says so.

### The network, power and money

- **Holding the network.** A thread holds it with `Online::hold` or `Online::keep`, only around requests in flight; a holder that asks for the time itself or had it asked in a stay before holds quietly (`Online::hold_quietly`, `Account::hold_quietly`), and nothing is asked beside its hold. What another thread does beside a hold, the clocks' check on the `time` thread, runs under a share of it (`Hold::share`), so no stay stands that nobody holds. No part is handed an `Online` for its work with OpenAI: the `Account` keeps the one it is made with and holds through it only where a key is kept (`Account::hold`, `keep_hold`, `write::ask_work`), but for the key's keeper's checks of a key. The Pokédex keeps an `Online` of its own for a name typed, which needs no key, Signal one for its own service, and the calls' part one for a call; the browser keeps none, and holds through the `Account` for a page it fetches itself too (`Job::IS_KEYED`); a stay taken without the key serves no work that needs it (`voice::is_stay_kept`). A stay's end is a `radio::NetworkDown` (`Hold::down`), which only the radio's thread raises; a connection and a service take the one of the stay they serve. The radio's thread hands holds out as funcore's `Wants` says, and while the device rests only where `app::Debts::is_resting` lifts the rest ([Network](firmware/network.md#holding-the-network)).
- **Askings in turn.** What its askers share and one asks at a time while the others wait for that asking, a DNS query, a stay's NAT64 search and the first time check, keeps a funcore `handoff::Turns` in its state: whether one asks, the count of ended askings, the failure of the last, and the waiters, which the asking's end hands back to be woken. A waiter waits through `dial::await_turn`, which ends with its own stay too. What is kept of an asking and who asks again are its subject's: the cache, the NAT64's prefix, the hourly time check.
- **Transport.** A service reached over a WebSocket where OpenAI offers one keeps no HTTPS fallback: the conversation's turns, the translator and reading aloud ([OpenAI](app/openai.md#the-conversations-turns)). Requests whose service offers only HTTPS, and background work, go over HTTPS.
- **Models and money.** A request's language model and effort are its use's (`Terms::thinking(Task)`), which the account holds as the main loop hands it the settings' (`Account::set_terms`); work paid for anew asks the account whether the month's limit lets it (`Account::paying`, `Account::check_limit`, `Terms::check_limit`), and is refused as `Fault::Limit` ([OpenAI](app/openai.md#spending-limit)). A new kind of paid work asks it the same way.
- **Transcription.** Every job said has the connection its words go over made ahead while it records, in one place (`voiced::take_stay`, as `Voice::should_connect_ahead` says); a note's recording, which may last as long as a meeting, is the one that does not. Every recording is written down by the one `openai::transcript::transcribe`, whole or with its words as they come: a note's sound, a name said to the Pokédex, a request said to the browser, a request said to the bell, a request said for the rundowns, a message said for Signal and one said to the robot. What it is of is a funcore `transcript::Subject`, which names it in the log and books it in the ledger (`Subject::book`); a new recording to write down is a `Subject` variant, never an entry of its own beside `transcribe`.
- **Background model work** goes through `write::ask_work`; `write::wait_work` asks after it as `summary::Watch::next` says, and work cut off is owed (`summary::Job`, kept in `account::State::jobs`) ([OpenAI](app/openai.md#models)). What a piece of it is of is a funcore `summary::Work`, which names it in the log, tells the use whose model writes it and books it in the ledger (`Work::to_name`, `task`, `entry`; a day's rundown by `summary::RUNDOWN`): a new kind of background work is a `Work` variant, never a pairing of its own in the shell. The news alone defers to its alarm ([News](app/news.md#fetched-later)).
- **Signal.** `domain::signal::state::State` alone decides when its thread holds the network: `need`, in which a request on its way over the open socket keeps it, awake or asleep; `is_off` asleep; and `next_fetch_s` for the one alarm that serves both ([Signal](app/signal.md#power)). Auto mode adds `Auto::is_pending` and its reply while that waits for the socket (`has_reply_waiting`, a term of `State::is_off`); what the thread takes off the board on a stay counts as on its way until the round's status tells so itself (`State::take_commands`). A stay hands it what its connection tells after each round (`Connection::status`), and `State::take_round` answers with the round's turn of auto mode, whether the stay ends and how long it waits; a start and the end of a stay count as fetches there (`State::note_files_read`, `State::note_stay_end`). A transfer of an attachment due or under way holds off a suspend and the radio's rest (`State::is_off`) and, awake, the stay until the device has taken what it ended in (`State::need`); the `attachments` thread carries them one at a time, each holding Signal's `Online` for itself. Its threads alone hold that `Online` and the partition its files are on (`Resources`), and the `signal` thread alone what else the partition keeps of the account (`files::Traces`: the uses and the ledger, which it has forget Signal once the phone unlinks the R1); auto mode's writer holds the `Account`, which reaches OpenAI through its own.
- **The device.** `Ui::tick` decides when the device sleeps (`IDLE_TO_SLEEP_NS`) and, on a cable, when what is billed by time ends ([Sleep and clock](firmware/sleep.md#sleep)).
- **Failures.** Why something asked of the network or a service came to nothing is an `openai::fault::Fault` ([OpenAI](app/openai.md#account)). impshell hands it on unchanged; the subject's funcore state makes it a `domain::cause::Cause` (`Cause::from_fault`), whose word the ui picks with `cause_word`, and decides waiting with `Fault::is_stalling` and asking again with `Fault::is_permanent`. A session ends as a `fault::Ending`. impshell names no word of a network or service failure.
- **Sessions.** A WebSocket is `websocket::Socket::reach`, read with `next_message` for its kind of message. OpenAI's sessions are one impshell `openai::Session<S>`: the reader's `ReadingSession` and the translator's `Interpreter` are aliases of it, and the conversation's `TurnSocket` holds a `Session<()>` ([OpenAI](app/openai.md#account)). A realtime service's messages go straight to its funcore state (`Reading::take_message`, the translator's `Session::take_message`). Timeouts sit in funcore beside their service.
- **The router.** `domain::router::Machine` decides everything the forwarder does and returns it step by step (`router::Step`), one effect each: when a stay is held and asked for anew, which way out a packet takes, and so that with the tunnel wanted a computer's packet has the tunnel's way alone (`Machine::path`); impshell's `router/` reads packets into it and does its steps. A packet is rewritten in one place, `net::nat`, whoever sent it and whichever way it leaves; a new way out is a `nat::Sink` and its arm in the machine, never a second table. The forwarder's thread never waits on the network, since the device's own packets pass through it: what must, a name looked up or a translation found, runs on a thread beside it under a share of its hold, and answers on the board ([Network](firmware/network.md#router)).
- **Calls.** `domain::calls::Machine` decides every step of the calls' thread and returns it one at a time (`calls::Step`), one effect each, as `domain::router::Machine` does the forwarder's; impshell's `calls/` reads sockets, the stay's end and the board into it and does its steps. A call holds the network from the owner's order, or from a one-to-one offer's arrival, whose answer goes before the owner sees anything, or from the owner's taking of a group's ring, to its end, and holds anew where its stay ends. Its requests to the calling server run on a thread beside it under a share of its hold (`Step::Fetch`, `Hold::share`) and answer on the board, so that the calls' thread waits on its sockets, its timer and its board alone; the call's sound runs on the card's threads, each on a side of its own, under a lock of its own that moves only what passes between them (`hw::sound::call::Sound`) and lends its holder the priority of a sound thread that waits for it (`sys::PiMutex`), and wakes the calls' thread where a packet waits; the far side's frames are decoded on a thread of their own, which the board hands them to and which hands back through it the senders of those that did not decode (`calls::state::Decoding`, `State::add_shown`). Whether Signal's socket stands for the calls is a term of Signal's `State::need` and `State::is_off` (`State::set_calling`) ([Calls](app/calls.md#power)).
- **A new user of the network** holds a `Hold` only around requests in flight, through the `Account` where its service needs the key, and adds no retry loop, timer or hold of its own: a this-time failure is retried only where its subject already retries one. A new session billed by time is wanted through a `Ui` method that returns none asleep, and is named in the pair `Ui::is_billed` and `Ui::end_billed`, which `Ui::deadline` and `Ui::tick`'s cable branch read. A new reason for Signal to hold the network is a term of `State::need` or `State::is_off`.

### The interface

- **Parts of the ui.** An element (`Item`, `Gauge`, a list's `Lines`, `Bar`, `TextRoom`, a `Keyboard`'s keys in `keys/`, the pictures' painters in `picture/`, the typed band and the secret line in `edit.rs`, `Robot`, `Corner`) has one drawing implementation and knows no screen or theme. A layout (`ui/layout/`) gives each element the style values of its look and places the gauges and the clock. `ui/view/` composes elements from state and reads the look. A screen (`ui/screen/`) maps state to elements and input to actions: it does not paint, branch on a theme or read the layout. `draw_*` takes the pen, `paint_*` makes pictures, `write_*` only builds strings.
- **The tree.** `TREE` (and `SUGGESTED` for the Companion's home) in `ui/screen/tree.rs` is the one tree of what the device does. Its only walked instance is `Ui.tree: Tree { levels, path }`, grown for the theme by `grow_tree`; each level shows as `Shape::Stage`, `Shape::Menu` or, a level that stands on a rail, `Shape::Rail`. It moves only through `open`, `level_back`, `go_home`/`tree_home`, `stand_at`, `show_on_level` and `reveal`, the one place what each level shows is reckoned from whether the debug screen is unlocked and Signal linked (`Presence`, `Gate`), which the unlock and the link's change both go through. `Use` is a leaf's action; `Screen` is what shows; `Screen::parent` says where a screen goes back to, for back and the trail. What a line of the tree tells under its name is written in one place, `Ui::write_node_word`; whatever changes what it reads deals the menu in front anew and asks for a frame while such a line or icon shows (`Ui::does_line_show`), the news of the parts and the conversation's acts through `Ui::redeal_lines`, the battery and the settings through their own setters. A new entry is a `Node` plus a `Use` or `Destination` variant with its word and its opening in `perform` or `open_destination`; a new child screen is one `Screen::parent` arm. Every screen the tree opens is a `Destination` and every level the conversation enters a `tools::Menu`, whose node is made by its name (`menu`) and found by it (`Ui::enter_menu`), and each has its word among `use_device`'s actions (`tools::parse_destination`, `tools::parse_menu`): a new screen or level of the tree gets one, so the conversation reaches what a hand reaches. A setting is set where its line stands, with no screen of its own: a `Setting` variant in `Setting::ALL`, its `setting` node, its value in `Settings::value` and `Settings::with_value`, its value's words in `Ui::write_setting`, its steps in `Settings::stepped`, its name and values for the robot in `Setting::to_name` and `Setting::parse_value`, and whether a change leaves the device as safe and as private as it is in `Settings::is_eased`, which says nothing of what it costs; `Ui::click_setting` and `Ui::change_setting` set it, one setting's value staged at a time (`Ui.staged`), which `Ui::let_go_staged` alone lets go of. Its node stands in the tree or in the list of a screen a `Destination` opens: that screen keeps its setting nodes and their icons (its `ICONS`, in `screen::ICONS`), counts them among its lines, lays them out with `Ui::node_item` and names them in `Ui::node_at`, and `settings::LISTED` gives the robot the destination that opens it.
- **Lists.** A list is a `List` key (`ui/view/lines.rs`) to its grid (`grid_of`), its lines (`item_of`) and its dealt state, the pictures of its lines among them (`store_of`). It opens with `show_lines`; the button's squeeze is taken and released once through `Ui::squeeze`, a stage's icon as a grid's place; the wheel reaches it through `wheel_lines`. A new list screen needs no wheel, release or landing code of its own.
- **Pictures in places.** A grid lays out its places and chooses among them; what stands in them is a `gfx::store::Store`, by the spot the grid gives each place (`Grid::spot_of`), which keeps the pictures, lets go of those whose spot the grid lays on no page (`store::Placements`), decides how a new one appears (it unfolds, or in a store that cuts, `Store::with_cuts`, stands whole at once), tells how far each shows (`Store::visible_area`), draws them, and keeps what a spot lets go of to draw its next picture into (`Store::spare`), where pictures of its kind are drawn on the screen's side (`AsPicture::IS_REUSABLE`). A list's lines are painted only where their spot holds no picture of their key (`Store::holds`), into what the spot let go of, and put with it; the themes' cards are painted into what their spot let go of too; the roll's small pictures and the drum's are put as they come (`Store::put`). A painter of a picture that stands in a place takes the words it draws into. A new screen of pictures in a grid keeps a `Store` beside its grid, advances it in `Ui::tick` by its grid and draws it through `Ui::draw_rows`. A picture without a grid stands in a store of one place (`store::SOLE`, laid by `store::SoleSpot`): a room kept under the bar (`RoomPlate`) and Dial's band. A picture that comes with its place is put to stand whole (`Store::put`, told so); one put anew where a picture showed unfolds. The bar subtitle, which is no picture, unfolds by a `store::Unfold` of its own.
- **Drawing.** A frame's drawing reads the `Ui` (`&self`) and changes nothing of it; `gfx::pen` alone knows which of its two passes runs. What a frame reads that is made for it is made before it, in `Ui::ready`. A picture a frame paints for itself goes through `Pen::plate` or `Pen::stretch_canvas`, keyed by all it shows, in a slot of `kit::Canvas` that `Ui::make_canvas_room` makes room for. The only state written while a frame is drawn is its scratch: the texts it writes into (`word`, `bar_text`, `run_time`), the mask, the canvases of plates (`Pen::plate`), the robot's list of outline points (`Robot::trace`), and whether a field ticked (`TickerClock::is_seen`) and the bar wrote its word (`BarWord::is_drawn`).
- **A change of theme.** `Ui::relayout` lays everything out anew from home, and every screen gives way to home (`Ui::theme_home`) but a screen of a setting, the safe's window, the bell's and a ringing call's, which stand over home from then on, and, for a theme the conversation sets, the conversation; while the key's window may not be left, the conversation sets none. A screen that keeps the picture of its room under the bar (`RoomPlate`) lays its rows out in one function of its own as it opens; the rows that outlive a change of theme, the conversation's, the Pokédex's result and the browser's page, are laid out anew by `Ui::reflow_rooms`, which also has every room cut its next picture in or unfold it as the theme does (`RoomPlate::set_cutting`); a palette worn has every room drawn anew (`Ui::renew_rooms`). The rooms are named once, by `view::rooms::TextRoomId`, whose `of` gives the room a screen fills and whose `ALL` `reflow_rooms`, `renew_rooms` and `advance_rooms` go over; what a plate does whatever keys its picture is `textroom::Plate`. A new such room is a `TextRoomId` variant with its arm in `Ui::plate`, `Ui::plate_mut`, `Ui::scroll_parts`, `ready_room`, `text_room`, `meter_row`, `land_screen` and `wheel_text`.
- **The window that scans.** One window takes by a scanned code what the device keeps, `screen::keying::Keying`, for what `scene::Scan` names: the key to OpenAI's services, or a tunnel's config. Its steps, its scan, its camera and its lines are one implementation (`Ui::take_scan`, `Ui::key_camera`, `Ui::key_item`), and only the key's may not be left while none is kept (`Ui::is_key_held`). Something new read off a code is a `Scan` variant with its arms there, never a second window or a scan of its own.
- **Keyboards.** One model in `ui/keys/`: `KeyboardId` (`ui/screen/typing.rs`) names each keyboard; `keyboard`, `keyboard_mut`, `keys_up`, `is_typing`, `is_typing_text`, `on_keys` and `end_typing` answer for all of them, and a keyboard's band and the room over it follow `keys_up`. A new keyboard is a `KeyboardId` variant in `KeyboardId::ALL` with its arm in `keyboard`, `keyboard_mut`, `keys_up` and `end_typing`, and in `is_typing_text` where it types a message or a name; one that has a screen to itself, as the password's and the PIN's, takes that screen's click and wheel through `keys_up` and lands with it in `land_screen`.
- **The button.** A press belongs to the screen it went down on (`Ui.pressed_on`). Where another screen has taken that one's place as it comes up, by a swipe, an act of the conversation's or the key's window, `Ui::let_go` lets go of what it was for and it is no click there; a hold at home whose screen another took is let go the same way, and so is a press a swipe came over, wherever the swipe goes. A sleep lets go through the same `let_go`. A screen left by a swipe, the bell, a call that rings, the rail or the press that wakes the device lets go of what it holds, a recording, a voice, the reading aloud of the browser's page and Signal's pictures, through `Ui::leave_screen` alone; a swipe back that only drops a Signal draft leaves nothing. The press that turns the screen on, out of a sleep or out of the dark of a task, is one `Ui::press_waking`: it clicks nothing, and held it talks, for the voice `Ui::talk_screen` names where the screen was dark. While the key's window may not be left (`Ui::may_key_be_left`), the conversation's acts open no screen over it.
- **Transcripts.** One wheel rule, `Ui::wheel_text`, for rows anchored at the foot (counting back from the newest) and pages read from the top. A new transcript screen adds one arm to its match and to `Ui::text_room`.
- **More below.** How a screen tells that more of what shows follows below is the theme's style (`ListStyle.has_arrow`, `BarStyle.has_pager`), read from one account of a page (`Grid::spare_rooms`, `Grid::has_more`) and of a text that scrolls (`Ui::text_room`): marks draw it (`list::draw_more`, `Ui::draw_scroll_mark`), the pager writes it on the status line in place of what the screen tells (`Ui::write_more`). A new paged or scrolled screen tells it through these and draws no mark of its own.
- **Motion.** Every edge that moves by itself is one row of `Ui::run_motions` (`ui/view/settle.rs`): its aim, its spring, its rest, whether its screen moves it, and whether it stands at its aim while unseen; the passage between screens and the robot's upright are rows too. The seat box's reset (`robot_place.at`, `robot_place.quarters`) stays outside the rows: it also sets the quarter turns, happens when the robot comes to show, is planted or changes its quarter turns, and snaps nothing while the robot is unseen. A bar that tells a span keeps a `Stopwatch`. The microphone's level is one `Meter` of the `Ui`, whatever records (`Ui::set_microphone`): its blocks are lit while the screen that shows hears (`Ui::is_microphone_heard`) and drawn by one function at that screen's place for them (`Ui::meter_place`, `Ui::draw_meter`), the first line of a list that records, a note's, the bell's request, the rundowns' or a call's own, or the row a room keeps (`Ui::meter_row`). A new screen that records adds its term to `is_microphone_heard` and its place to `meter_place`, and nothing else: no meter, peak, motion row or painter of its own. What is put anew where something showed unfolds through `gfx::store` (see Pictures in places), never by an edge of its own, and Terminal cuts it in (`Ui::does_cut`).
- **Voice jobs.** A job said or typed (the conversation, the browser, the bell's request, the rundowns' request, the Pokédex, Signal's dictation) is a funcore `voice::Job` held as `Voice<J>`, which decides what a recording becomes ([Chat](app/chat.md#a-turn)), send-or-drop when the job is wanted no more, how long the network is held and whether through the key (`Job::IS_KEYED`, `voice::is_stay_kept`); plus an impshell `voiced::Worker` with `stay`, `turn` and the stay's end, `DOWN`, the state told what the turn thread has of the network (`voice::Hold`), so that a turn whose inputs wait fails by the refusal of the stay just asked for (`Step::Fail`) and the network is asked for no second time at once; plus a `screen::voice::Voice` on its screen, named by a `VoiceId` with its arms in `Ui::voice`, `Ui::voice_mut` and `Ui::does_voice_show`, by which `Ui::voices`, which the Ui's rules of use, its deadline and the robot's activity read, and `Ui::count_voice_seconds`, which counts every voice's seconds for `settle`, go over all of them, its press let go by `Ui::let_go`. While the job listens its screen keeps a row for the microphone's level, a `LineKind::Meter` line under a transcript's rows (`TalkForm::push_meter`), the row over a page or the first line of the bell's list or the rundowns' (`Aside::Meter`; see Motion). The job of a request read into changes of what the interface holds, the bell's and the rundowns', is one `voice::Request<S, C>`, by what a request is read against and what a change is (`bell::state::Setter`, `news::request::Asker`). A list whose first line takes a request, the bell's and the rundowns', is a `screen::voice::RequestList` and keeps one `screen::voice::RequestLine<C>`: its voice and the bids a hold, a click on that line and a request in words make, each with what the request is read against (`C`, the list as it stands); its press, release, drop and leave are the one `Ui::press_request`, `release_request`, `drop_request_press`, `leave_request_list` and `let_go_request`, by that key. A new such list keeps a `RequestLine`, adds its `RequestList` variant with its arm in each of them, and writes no press, release or drop of its own. A screen of one page under the bar that such a job brings, the Pokédex's and the browser's, is a `screen::voice::PageId`, and what it keeps is one `screen::voice::PageScreen`: its voice, its keys and their band, its bids, its page (`ScreenPage`) and its rows in their room. Its room, its keys' band, its scroll and the row of the microphone's level over its page are laid out by the one family of `paged_*` functions in `ui/view/rooms.rs`; it opens, lays its rows, lands and shows a page through `Ui::open_paged`, `lay_paged`, `land_paged` and `show_page`, its keys go up and down through `Ui::toggle_paged_keys`, and its voice's phase is taken by `Ui::take_paged_phase`; a new one adds its arm to `Ui::paging`, `Ui::paging_mut`, `Ui::page` and `take_paged_phase`, and lays out nothing of its own. A world check or extra asks go in the worker's `READY_CHECK` / `CHORE` consts.
- **Numbered asks.** A screen's ask that a part answers by number (the translator's session, a reading aloud) is a `screen::Round { number, is_on }`: it stands connecting from the ask on, and `Round::note_phase` alone takes the part's word on it, ending it once that word says it is over. The reader reads what `Ui::reading_request` picks ([Audio](app/audio.md#reading-aloud)).
- **The robot** reacts through `Robot::react(Reaction, now)`; the Ui calls `Ui::react`, whose one gate is `Ui::does_robot_live`, and never `Robot::react` itself. A new reaction is a `Reaction` variant and its gesture.
- **Themes.** A theme is a `Layout`: a `Look` of one style value per element and variation (`ListStyle`, `BarStyle`, `RoomStyle`, `KeysStyle`, `CaretStyle`, `RollStyle`, `CornerStyle`, `HomeStyle`, `Motion`), and where it places the gauges and the clock (`Layout::place_gauge`, `Layout::place_clock`). Where its look has a rail (`Look.has_rail`), a level whose lines each open something, none setting a value or only telling, grows as `Shape::Rail`: entered, it stands at the left of every screen, beside it its lines show in the pane, its one grid laid out where it stands (`Ui::seat_level`), and the `Ruler` lays everything else out right of the rail (`Ruler.left`): a new layout of a screen starts from `Ruler::under_bar` and `Ruler::centre_left`, never from the panel's left edge. `ui/view/rail.rs` is the rail's one home: which level it shows and its list (`Ui::rail_list`), whether the wheel turns it (`Ui::does_rail_turn`, `Ui::does_rail_lead`), the screen the button and the wheel reach meanwhile (`Ui::entered_screen`), what the pane follows of the line it rests on, which `Ui::tick` opens through `perform` with the wheel left on the rail, and where it stands while the conversation shows over what a hold or a photo for the robot opened it over: on `CHAT`'s line until going back returns it (`Ui::stand_rail_on_chat`, `Ui::return_rail`); the screens' input, marks and keyboards ask it, and no screen opens or closes anything for the rail of its own. Each line role takes a `Form` (`ListStyle::form_of`), and a line that has a form of its own whatever its role, a palette's in a typed list, takes that (`ListStyle::form_for`). The interface asks `look()`, never a theme's name. A new variation becomes a field only where no existing field names it; a new way to draw a role is a `Form` and its arm in `Item::paint`.
- **Pictures of lines** are keyed by the `Item`'s derived `Hash` (`Item::to_key`), so a new field of `Item` is part of its key without more code.

### Kept files

A kept file is a directory and a name: the name a `pub const` of the funcore module that owns its format, the directory one of that module too, or of `storage` where files of several modules lie in it (`storage::INTERFACE`, `storage::CHAT_PRIVATE`). impshell reaches every kept file through `storage::Data` ([Storage](firmware/storage.md#the-data-partition)), each part through one narrowed to the directories it uses (`Storage::within`, bound in `start.rs`), which nothing that holds it widens; the USB drive and the debug shell alone hold it whole. Key-value lines are read with `base::lines`: `value` (a key's first line), `last_value` (its last line whose value reads, so that a later line overrides an earlier one), `values` or `numbers`; the known networks and their places, whose lines come in pairs and in a fixed order, are read in order by `wifi::known` and `wifi::places`. A family of files is named by an enum that both names and recognises them (`File::to_path` / `File::from_path`). A new kept file adds its constants, a round-trip test of its format, its line in `file_paths_stable` and in [Storage](firmware/storage.md), and its directory to the scope of the part that keeps it, where that does not reach it yet.

### Media and hardware

- **The microphone.** `sound::capture` alone switches it on and reads it, hands on each block with the samples recorded after it that wait to be read, as the card tells them (`Capture::Samples`), a block whose read or whose delay's read after it meets an overrun going into the gap counted from the clock (`Capture::Gap`), and tells the card's state every block's largest sample (`CardState::hear`) where no other thread holds that state just then, as the sound's threads never wait for it, the speaker keeping the gain it last read there; the card's state stands on a `sync::Board` whose flag the main loop watches (`Source::Microphone`). `sound::record` and `sound::record_voice` add a file to it, and a call's sound takes its blocks as they come. No recording, job or report carries a level of its own; a call's packets carry the level RFC 6464 has the calling server read, for the wire alone.
- **Registers.** impshell's only `Hardware` is `sys::Registers`, built next to each node's mapping call and handed to funcore's sequences; where a register lies is funcore's `hw::locate`.
- **Wanted work.** `handoff::Request<T>` holds what the screen wants of a part's thread, its clicks and whether the thread is busy, and alone decides that: a thread serves a request while it stands (`serve`), or takes each request up at once and begins it once (`claim`, `next_new`, `begin`). The camera, the gallery, the translator and the reader hold one, and their states' `is_off` is that the thread is not busy.
- **Crews.** A job cut into parts runs on an impshell `Crew`: its items through `Crew::for_each`, its parts, each a funcore `base::crew::Part`, through `Crew::work`, and a step's `base::crew::Work` through `Crew::run`: parts at once, or a `Wave`, rows of places each taking a place once the row above has finished a lead of places past it, beside parts that never wait (`Work::in_order` runs either on the caller's thread alone). A wave's rows note and read their counts of places done in a `Progress`, without a lock, and hand what the rows below read through a `Handoff`, bytes put before a row notes its progress and taken once the row below finds its place ready. Work of funcore's that a crew runs hands its parts to a function its caller gives (`vp8::Encoder::code_steps`, `develop::Developer::new`, the bench's `code_on` and `make_on`), so that it holds no thread. A picture of any sample is cut into bands of whole lines, a part each, by `gfx::bands`: a viewfinder's drawing, a video's, a JPEG's painting and the local tone map's passes among them. A crew is placed by `Crew::on_cores` with its calling thread, or by `Crew::with_cores` alone ([System](firmware/system.md#the-app)).
- **Buffers of a DMA master** come from the ION its node opens above itself (`Lock::ion`, `Jpeg::ion`, `Isp::ion`): a dying process closes descriptors lowest first, so the master stops before its buffers are freed. No other code opens ION (`Ion::open`); the camera's stream buffers and a photo's burst come from its own node's (`Rig::ion`, `frames::Frames`), a photo's planes and file from the JPEG encoder's, which the darkroom alone claims, for the first burst or copy it works on, and lets go of once nothing waits (`PhotoBuffers`, `Work::Release`), and the H.264 encoder's are its own (`Venc::open`). What a DMA wrote is read through the call that makes the CPU forget it first (`Buffer::dma_bytes`, the file `Jpeg::encode` returns, `Venc::stream`), and what the CPU wrote for a DMA is flushed by the node that starts it.
- **Bits** are read through `bits::BitReader`, highest bit first (AAC, H.264, QR codes, VP9's frame headers); `BitReader::with_escapes` reads H.264 past its escape bytes. The reader's one exception is JPEG's scan, read by `Bits` in `codec::jpeg::decode`: it keeps 64 bits ahead so that a Huffman code is looked up 9 bits at a time, where `BitReader` reads bit by bit, and it passes over the byte stuffed after 0xFF and reads zeros from a marker on. They are written through `bits::BitWriter`, highest bit first and filled up with zeros (AAC, H.264, QR codes). The writer's one exception is Zstandard, whose streams fill each byte from its lowest bit and end in a set bit their reader finds from the back (RFC 8878): `codec::zstd::bits::Bits` writes them. An entropy coder is no bit format and is its codecs' own, one for each: Opus's range coder (`codec::opus::range`), and the boolean coder VP8's decoder and encoder and VP9's decoder share (`codec::boolean`). A new bit format reads through `BitReader` and is written through `BitWriter`.
- **Pictures.** RGB becomes JFIF 4:2:0 through `ycbcr::jfif_luma` and `jfif_chroma`. Y, U and V become the screen's pixel words a row at a time through `Colours::row`, a row's colours apart, side by side or a pair for two pixels (`ycbcr::Chroma`): a JPEG decoded, a video's picture (`hw::projector`), a photo's planes (`planes::to_words`) and the far side's picture of a call. A JPEG is decoded at 1, 2, 4 or 8 samples of each block's 8, the fewest that give the size it shows at (`Jpeg::plan`), and a video's picture is shrunk by a step of 1, 2, 4, 8 or 16 samples each way, the largest that leaves it no smaller than its view, each sample the mean of those its step covers (`hw::projector`); each then takes for every pixel the mix of the four samples about its middle (`sampling::Place`, `blend`, `pick`), which shrinks or grows it the rest of the way. The far side's picture of a call is shrunk by the mean of what each sample covers (`planes::Cover`, which takes a plane of at most 65535 samples a side and 8388608 in all, `MOST_SIDE` and `MOST_TOTAL`) or grown by that mix of four; a photo's planes are only shrunk, by the mean (`planes::Shrink`, over `Cover`), for its review and the pixel cam. A picture of words is turned by `sampling::turn_words`.
- **Filters.** A row of samples filtered by taps, its edges mirrored, is `sampling::filter_row`, a picture's rows filtered down `sampling::filter_down`, both over `sampling::sum_rows`, for bytes, halves, words and floats (`sampling::Weigh`): the photo's alignment pyramid, its local tone map's pyramids and its sharpening (`hw::camera::align`, `fusion`, `sharpen`). A codec's prediction filters through `simd::filter`.
- **Sums of products.** A sum of the products of two runs of samples, or of their squares, is `base::math::dot`, in one order of additions on every machine, four running sums over each 16 values: the resampler, CELT's pitch, analysis and bands, the AAC encoder, the leveller, a call packet's level, the echo canceller and the jitter buffer's acceleration. A complex product, a point turned by a turn or by its conjugate, is `fft::rotate`: the butterflies of the FFT's stages, each over whole rows of points (`fft::Plan`), the AAC transform's turns, CELT's MDCT's and the echo canceller's products of spectra.
- **Vector kernels.** A loop over blocks of bytes or words that NEON runs faster is a kernel of `base::simd`, slices in and out, named for what it computes: `sad` and `sad_mean` for VP8's motion search, `satd` for its choice of modes, over whole blocks of 4x4, `filter` for the taps of VP8's and VP9's predictions and of VP8's half-pixel planes, `plain::tap` for a filter whose taps change from byte to byte, `columns` and `put_columns` for a block of 8 lines of 8 bytes turned to lanes of its columns and back, the loop filters' segments along lines (`codec::edge`), `words` for the pixel words of a row (`Colours::row`), `Sample::turn` for a picture of words, bytes or blue and red pairs turned (`sampling::turn_words`, the projector's bands), and `unpack` for the camera's packed codes of 10 bits (`raw::Raw::line`, `video::Planes`' lines). A kernel has a safe function that takes the NEON body where the block fits it, its plain body in `plain`, a test that holds the two equal, and an entry in the bench's `KERNELS` (`domain::console::bench`), `columns` and `put_columns` one together; `plain::tap` alone is a plain body, with no NEON body or entry of its own. No other module calls an intrinsic, and a loop another module also runs calls the kernel in place of a copy of its own.
- **Stills.** A JPEG is decoded to the screen's pixels by `media::still::decode`, for the roll and for Signal's photos alike; the turn its EXIF orientation asks is read as `Jpeg::read` passes its segments (`Jpeg::orientation`) and made by `jpeg::oriented`, which also mirrors the front camera's pictures in a photo's review (`camera::Sight`). A PNG's image data is inflated by `media::still::inflate`, for Signal's photos and the Pokédex's artwork alike.
- **Forms.** The H.264 decoder and the video side of the MP4 reader take what our recorder writes and the plain foreign H.264 and MP4 that need nothing more; any other form is refused by name with one `codec::Flaw` ([Media](firmware/media.md#videos)). The AAC decoder and the sound side of the MP4 reader take what phones record too: low complexity AAC of one channel or two at any rate of the standard's, in MP4, QuickTime or ADTS ([Media](firmware/media.md#aac)). A call's codecs take what Signal's apps send: Opus in every mode, VP8, and VP9 of profile 0, each decoded picture one `codec::picture::Picture` ([Media](firmware/media.md#opus)). A new form is read only where the device's own recordings, the sound sent by its owner's phone or a call's far side need it.

### The console

`domain::console` owns the protocol: `Command` (`parse`, `encode`, `refusal`, `ends_link`), the verb names (`VERBS`, `SHELL_VERBS`) and `wire::Reply`. On the device a verb answers into the `Reply` at once, sets a field of `Requests` that `steer` hands to the part already doing that work, or goes to the shell's thread if it waits on files. A new verb is a `Command` variant with its round-trip entry, its name in `VERBS` or `SHELL_VERBS`, and its row in [Console](firmware/console.md); it never gets a thread, a job type or a device path of its own. The `bench` verb alone starts threads and crews of its own, by `Crew::on_cores` on the large cores as a call's pictures take them and on every core as the camera takes them, since work times as the device's own only on those cores, each thread ending with its work, and alone reads where each case ran: its core (`sched_getcpu`) and the clusters' clocks (`sys::CLOCKS`, which the logs' snapshot reads too). What the shell reaches only for a host that gave the safe's passphrase is decided in one place, `shell::Gate` with `shell::is_path_denied` and `Command::needs_gate`, the config a `tunnel` verb hands over among it (`shell::State::read_tunnel`), which the router's thread then keeps as it keeps one the window read; what a backup takes, what stays the device's own and the steps of a restore are `domain::backup`'s ([Storage](firmware/storage.md#backup-and-restore)).

### Tests

| Code | Checked by |
|---|---|
| funcore below `ui` (`base` to `domain`) | host tests in a `#[cfg(test)]` module of the code's own module (`mod tests`, or `tests.rs` beside it), of every decision, format, protocol and state machine |
| a kept file's format | its round-trip test ([Kept files](#kept-files)), and `tests/fixtures/`: files as earlier firmware wrote them, read and written back byte for byte |
| funcore's `ui` | the shot renders, never a test: `examples/shot.rs` keeps its own data and renders screens to PNG files to look at, and no test reads them. No test drives a `Ui`, a screen, an element or input; only a pure function that turns values into a screen's text has one beside it (`pokedex::to_text`, `memos::to_brief_name`) |
| impshell | tests of the world alone, as `tests/boundaries.rs` holds them ([The law](#the-law)): the network through `net::served`, a wait on one part's flag through `Epoll::with_fd` |
| r1-image, r1-flasher | host tests beside the code |
| the kernel | none; `boundaries.rs` holds its tracked files to patches and configuration |

A type's test builders live in a `#[cfg(test)]` module of its own file (`tests`, `fake`, `support` or `samples`), and other tests import them. Each funcore crypto trait but `crypto::Primitives` has a fake beside it, which stands in for `Primitives` too where its trait is built on it: `Sums` for `wpa::Crypto`, `Standin` for `signal::Crypto`, `wireguard::tests::Toy` for `wireguard::Crypto` and `crypto::X25519` and for `net::rtp::Crypto`, a stream of hashes in place of AES-GCM, `net::stun::tests::Exact` for `net::stun::Crypto`, the standards' hashes over random bytes of a seed, and SAE's two `Toy`s, a toy group for `sae::Curve` and a toy curve for `sae::point::Field`; a call's machine is tested under `Standin` given STUN's exact hashes and SRTP's toy, so that it is a whole `domain::calls::Library`. Beside `Standin` stands `Exact`, whose SHA-512, SHA-256, SHA-1, HMAC-SHA256, HKDF-SHA256 and AES-256 in CTR mode are the standards' own, so that libsignal's own vectors hold for zkgroup's arithmetic, the chains' keys and the access keys, and a signature another key made is refused; beside the toy for SRTP stands `net::rtp::tests::Exact`, whose AES and AES-GCM are the standards' own, for RFC 7714's and RFC 3711's vectors. The standards' own primitives these reckon by are one module of the tests, `crypto::exact`, held to the standards' vectors.

## The shape of the code

- A getter reaches past its module (`pub`, `pub(crate)` or `pub(super)`, as far as its callers lie), which leaves its field read-only outside it, or is a trait's method; inside a crate any other plain read is of the field itself.
- An item reaches as far as its users and no further: private where its own module alone uses it, `pub(super)` where its parent module does, `pub(crate)` across its crate (in a binary `pub` or `pub(crate)`, which reach as far), and `pub` in a library only where another crate uses it. What only tests use is test code (`#[cfg(test)]`). `r1 visibility` checks both; it leaves alone what is compiled on some platforms alone, what such code names, and a method named as a trait's method is.
- A type whose fresh state is all defaults derives `Default` and has no `new`, but for a `const fn new` that a static needs (`net::dns::Cache`, `handoff::Turns`) or where `Default` cannot be derived (`camera::tone::Scratch`, of arrays of 256). `proto::Writer` and `ui::screen::finder::Painting` are the exceptions.
- A trait has more than one implementation, or it is one of the law's boundary traits.
- `Deref` is for smart pointers, never for reaching a field.
- A handle that funcore state holds for impshell is let go of in funcore's methods, under its board's lock, so its drop touches nothing of the world.
- A type that holds a key, a password or a credential tells none of it where it is formatted: it has no `Debug`, or one of its own that leaves it out (`safe::Passphrase`, `safe::Slot`, `Flash`, `known::Network`, Signal's `Account`, `Pair`, `Device` and `service::Frame`), and a protobuf being written or read tells its size alone (`proto::Writer`, `proto::Message`). Of Signal's types, one that carries a message's words, the sound of one said, a contact's name or with whom a message is leaves those out too (`Entry`, `Outgoing`, `drafts::Recording`); a contact's `ServiceId` tells its kind alone, so nothing that holds one tells with whom.
- A function returns what its caller uses; a struct that the one caller takes apart at once is not written.
- A change may add lines where it clearly makes the code better: one concept instead of two, a decision moved into funcore, a rule followed everywhere. Sizes are measured, never guessed.
